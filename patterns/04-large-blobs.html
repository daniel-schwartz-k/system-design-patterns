Handling Large Blobs

Photos, videos and documents are too big to push through your API servers. Let clients talk to object storage directly using short-lived signed URLs, upload in resumable chunks, serve downloads from a CDN, and let the storage system, not the client, tell you when a file has really landed.

Object storage Pre-signed URLs Multipart uploads CDN Metadata consistency

TL;DR

Uploading a 4 GB video to YouTube is the same problem as uploading a large file to Dropbox or Google Drive. If every byte flows through your application servers, those servers become expensive, slow, fragile file relays. The fix has a standard shape. Work through it in this order:

  1. Store the bytes in object storage (S3, GCS, Azure Blob), not in your database and not on app-server disks. Keep only metadata (owner, name, size, status, storage key) in the database.
  2. Take the app servers out of the data path. The server hands the client a pre-signed URL: a short-lived, narrowly scoped permission to write one specific object directly into the bucket. The client uploads straight to storage.
  3. Upload in chunks (S3 multipart upload, GCS resumable sessions, the tus protocol) so big files upload in parallel and a dropped connection costs you one chunk, not the whole file.
  4. Let storage tell you when the object landed. Use an event notification (S3 to SQS/SNS/Lambda) to flip the database row from pending to uploaded. Do not trust the client to report success.
  5. Serve downloads through a CDN with signed URLs or cookies, keeping the bucket itself private.

The part interviewers probe hardest is the last-mile consistency: your database and the blob store are now two systems that must agree, and any gap between them (client vanishes, event is lost, event arrives twice) must have a designed answer.

Recognize it when…
  • Users upload or download photos, videos, audio, documents, backups or datasets (YouTube, Dropbox, Google Drive, Instagram, Slack file sharing, a medical imaging archive).
  • The prompt says "large files", "gigabytes", "videos", "resumable", or "flaky mobile connection".
  • You catch yourself drawing an arrow from the client, through an API server, into storage. That arrow is the smell.
  • A feature needs both searchable metadata (title, owner, tags) and big opaque payloads in the same flow.

The problem

The obvious first design is POST /videos with the file as the request body. The API server receives the bytes, perhaps validates them, and writes them to storage. For a 200 KB avatar that is perfectly reasonable. For a 4 GB video it breaks in several independent ways:

  • Bandwidth is doubled. Every byte enters your server from the client, then leaves again towards storage. 1,000 simultaneous uploads at a modest 20 Mbps each is about 20 Gbps of ingress and 20 Gbps of egress through machines you pay for and must scale, just to relay data.
  • Connections are held for a long time. At 20 Mbps, 4 GiB takes roughly half an hour. During that time one worker thread, socket or event-loop slot is pinned to one user. A fleet sized for fast request/response traffic (milliseconds per request) is suddenly sized by slow uploads.
  • Memory and disk pressure. Servers must either stream carefully or buffer, and buffering gigabytes to memory or temp disk per request does not scale. A few large uploads can starve ordinary API calls on the same box.
  • Intermediaries have limits. Reverse proxies, load balancers and API gateways commonly enforce request-size caps and idle or total timeouts (for example nginx defaults to a 1 MB body limit, an AWS ALB idle timeout defaults to 60 s, API Gateway caps payloads around 10 MB and Lambda synchronous payloads around 6 MB; check current limits). A single long HTTP request across all of these is fragile.
  • Any failure restarts everything. A single HTTP request is all-or-nothing. If hotel Wi-Fi drops at 3.9 GB, the user begins again from byte zero. Retries also re-consume all that bandwidth.
  • Scaling cost is coupled to the wrong thing. You would scale your stateless API tier by gigabits of file traffic instead of by request rate, which is far more expensive.

Why object storage, and why not the database

Blobs belong in object storage: S3, Google Cloud Storage or Azure Blob Storage. Know how it differs from what you already use:

  • Flat namespace. A bucket holds objects addressed by a key string like uploads/u42/9f3c.mp4. The slashes are just characters; there are no real directories or inodes.
  • Immutable objects. You write a whole object or replace it entirely. You cannot append or edit bytes in place the way you would with a file. (Versioning can keep old copies.)
  • Very durable and cheap. Providers advertise about eleven nines (99.999999999%) of annual durability by spreading data across multiple devices and facilities. Storage is cheap per GB, and capacity is effectively unlimited. You pay for requests and data egress.
  • An HTTP API, not a filesystem. PUT, GET, HEAD, DELETE, list-by-prefix, and range reads. This is exactly why clients can talk to it directly over the internet.
  • Strongly consistent for reads after writes on S3 (since late 2020), so once a PUT returns success, a GET sees it. Other providers offer comparable guarantees; confirm for the one you pick.

Storing blobs inside a relational database is almost always the wrong call at this scale. It bloats rows and tables, evicts hot index and data pages from the buffer pool, slows backups and replication (every replica now copies gigabytes), makes the database the bandwidth bottleneck, and costs far more per GB than object storage. There is no native CDN integration either. (Very small blobs, such as tiny thumbnails under a few hundred KB, are sometimes kept in the database for convenience, but that is the exception.) The standard split is: database holds metadata and a pointer; object storage holds bytes.

Do the math out loud

Say the numbers: "If 1M users upload a 100 MB video per day, that is 100 TB/day of ingress, about 1.2 GB/s on average. I do not want that going through my API fleet. I want it going straight to object storage, which is built to absorb it." Then note that metadata is tiny by comparison (a few hundred bytes per file), which is why the database stays small and fast.

When it comes up

Any design where users move files or media of non-trivial size:

  • YouTube / Netflix / TikTok: upload a source video, then process it into many renditions and stream segments from a CDN.
  • Dropbox / Google Drive / OneDrive: large files, resumable sync, deduplication, sharing links.
  • Instagram / Pinterest / Flickr: photos uploaded, thumbnailed, served at huge read volume.
  • Slack / email attachments / chat apps: user files with virus scanning and access control.
  • Ticketing, medical and enterprise systems: PDFs, scans, exports and backups.
  • Any "and the user can attach a file" requirement hiding inside another design. Spot it and spend two minutes on this pattern.

Solutions, in escalation order

Start with the naive design so you can explain precisely what is wrong with it, then layer on the fixes. Each step solves a specific failure of the step before it.

Step 0The naive approach: proxy through the app server

The client sends the file to your API, which writes it to disk or to S3. Mention it, name its flaws (above), and say when it is acceptable: small files (a few MB at most, such as avatars or short documents), low volume, or a prototype. Even then, enforce a hard size limit at the edge. Beyond that, you need to move the bytes off your servers.

Step 1Pre-signed URLs: let the client upload straight to storage

The key insight is to separate the control plane (who may upload what; small JSON through your API) from the data plane (the bytes; straight to storage). Your server authenticates and authorizes the user, decides the object key, and then signs a URL granting temporary permission to perform one operation on that one key.

What a pre-signed URL actually is

It is an ordinary storage URL with extra query parameters carrying: the credential identity that signed it, a timestamp, an expiry, the list of signed headers, and a signature. The signature is an HMAC (AWS Signature V4 uses HMAC-SHA256) computed over a canonical description of the request: HTTP method, bucket and key, expiry, and any signed headers such as Content-Type. The secret key never leaves your server. When the request arrives, S3 recomputes the signature and checks that it matches, that the URL has not expired, and that the signing identity still has permission. Change any signed detail (a different key, method or content type) and the signature fails. Your app servers are not involved at all at upload time.

Properties to be able to state precisely:

  • Scoped: one bucket, one key, one HTTP method (PUT to upload, GET to download).
  • Short-lived: typically minutes (say 5 to 15) for uploads. The maximum is bounded by the signer: up to 7 days with long-lived IAM user credentials in SigV4, but no longer than the session lifetime when signed with temporary credentials (for example an assumed role or a Lambda role).
  • A bearer token: anyone holding the URL can use it until it expires. No further login is checked at storage. Treat it like a password: never log it, keep the TTL short, serve it only over HTTPS.
  • The server picks the key. Never let the client choose the object key or path (collisions, overwriting other users' files, path tricks). Use something like uploads/{userId}/{uploadId} with a random uploadId.

PUT vs POST policy: enforcing size and type

A signed PUT URL is simple, but it cannot enforce a range of acceptable sizes. You can sign the exact Content-Length (the client must then send exactly that many bytes) and the Content-Type. A pre-signed POST (browser form upload with a signed policy document) supports conditions such as content-length-range (min and max bytes), required key prefixes, and exact or prefix-matched content types. Use POST when you need server-enforced size limits on a single-request upload, or validate and cap sizes at the application layer when you issue multipart URLs (you declared the size up front and you control the number of parts you sign). A single PUT or POST to S3 is limited to 5 GiB; anything larger must use multipart.

# Python / boto3: issue upload permission (server side)
import boto3, uuid
from botocore.config import Config

s3 = boto3.client("s3", config=Config(signature_version="s3v4"))
upload_id = str(uuid.uuid4())
key = f"uploads/{user_id}/{upload_id}"        # server chooses the key

# Option A: presigned PUT (can pin Content-Type, cannot cap a size range)
put_url = s3.generate_presigned_url(
    "put_object",
    Params={"Bucket": "acme-media", "Key": key, "ContentType": "video/mp4"},
    ExpiresIn=900,                              # 15 minutes
)
# Client MUST send header Content-Type: video/mp4 or the signature fails.

# Option B: presigned POST (can enforce a size range via the policy)
post = s3.generate_presigned_post(
    Bucket="acme-media", Key=key,
    Fields={"Content-Type": "video/mp4"},
    Conditions=[
        ["content-length-range", 1, 5 * 1024**3],     # 1 byte .. 5 GiB
        ["eq", "$Content-Type", "video/mp4"],
    ],
    ExpiresIn=900,
)
# Client sends multipart/form-data using post["url"] and post["fields"].

# Limits worth remembering:
#  - single PUT/POST object max is 5 GiB; larger needs multipart upload
#  - bucket CORS must allow the browser origin and PUT/POST + headers
#  - signing is local CPU work; it makes no network call to S3
#  - URL expiry is bounded by the credentials that signed it

Pros

  • API servers handle only tiny JSON requests
  • Upload throughput scales with the storage service, not your fleet
  • No per-request memory, disk or long-held connections on your tier
  • Permissions stay narrow, auditable and expiring

Cons

  • Database and storage are now two sources of truth
  • Signed URL leakage grants write access until expiry
  • Needs bucket CORS and a client that can speak to storage
  • Validation (size, type, content) moves to after upload or into policies

Step 2Multipart and resumable uploads

One PUT is still all-or-nothing, and it caps at 5 GiB. For big files, split them into parts, upload each independently (and in parallel), and ask storage to stitch them together at the end. The benefits are the ones the video called out: if the connection drops, only the in-flight part is lost; the client retries that one part and carries on.

How S3 multipart upload works

  1. Initiate. CreateMultipartUpload returns an UploadId.
  2. Upload parts. Each part is sent with UploadPart, tagged with a PartNumber (1 to 10,000) and the UploadId. Each response returns an ETag you must remember.
  3. Complete. CompleteMultipartUpload with the ordered list of (PartNumber, ETag) pairs. S3 assembles the final object, and only then does the object become visible.
  4. Or abort. AbortMultipartUpload frees the parts. Until you abort or complete, the uploaded parts sit invisibly in the bucket and you are billed for storing them.

Limits to remember (S3; confirm current values): each part is 5 MiB to 5 GiB (the last part may be smaller than 5 MiB), at most 10,000 parts, for a maximum object size of 5 TiB. Part size choice is a trade-off: small parts mean cheaper retries and finer-grained progress but more requests and hit the 10,000-part ceiling sooner (a 100 GiB file needs parts of at least ~10 MiB); large parts mean fewer requests but more wasted work on a failure. 8 to 64 MiB is a common range, and clients usually pick the part size from the file size.

With pre-signed URLs, the server initiates the multipart upload and then signs one URL per part (upload_part with UploadId and PartNumber), or the client asks the server for batches of part URLs as it goes. Completion should ideally be done by your server (or a trusted worker) so that you control the final part list.

Resumability and client-side bookkeeping

Resuming means the client must know which parts already made it. Two sources of truth, and the second is safer:

  • Client-side state: persist UploadId, file fingerprint (name, size, last-modified, maybe a hash of the first chunk) and the completed (PartNumber, ETag) list in localStorage/IndexedDB or on disk. Cheap, but breaks if the user switches device or clears storage.
  • Ask storage: call ListParts(UploadId) (via your server) to learn exactly what S3 holds, then upload only the missing parts. This is authoritative and survives client crashes. The server can also store UploadId in the metadata row so any device can resume.

The same ideas exist elsewhere under different names:

  • Google Cloud Storage resumable uploads: you initiate a session and get a unique session URI. You send bytes in chunks (multiples of 256 KiB) with a Content-Range header. After an interruption you query the session URI for how many bytes were persisted and resume from that offset. Sessions last on the order of a week.
  • Azure Blob: Put Block for each block, then Put Block List to commit, with SAS tokens as the pre-signed equivalent.
  • tus protocol: an open HTTP-based resumable upload standard. The client creates an upload, HEADs it to learn the current Upload-Offset, then PATCHes from that offset. Server implementations (tusd) can sit in front of S3, and client libraries like Uppy support tus and S3 multipart.

Integrity: checksums

Networks and bugs corrupt bytes, and you want to catch it before declaring success. Send a checksum with each part: Content-MD5 (classic) or the newer x-amz-checksum-sha256/crc32c headers, and S3 rejects a part that does not match so the client simply re-sends it. Remember that for multipart objects the final ETag is not the MD5 of the file (it is a hash of the part hashes with a -N suffix), so do not use it as a content hash. If you need an end-to-end file hash (for dedup or verification), compute SHA-256 on the client and store it in metadata, or use S3's additional checksum support.

Pros

  • A dropped connection costs one part, not the whole file
  • Parallel parts saturate fast links and finish sooner
  • Supports files far beyond the single-request limit (up to 5 TiB on S3)
  • Per-part checksums catch corruption early
  • Pausable and resumable across sessions

Cons

  • More client logic (chunking, retries, progress, concurrency)
  • Many more signed URLs and requests to manage and pay for
  • Incomplete uploads leave billable orphan parts unless cleaned up
  • You must choose and tune part size

Step 3Keep metadata and blob consistent: let storage tell you

Now the subtle part. You have two systems: your database (a files row) and the bucket (an object). No transaction spans both. Things that can go wrong:

  • The upload succeeds in S3, but your row still says pending (the client never called back, or called a crashed server).
  • The row says uploaded, but the object is missing or incomplete (a lying or buggy client reported success).
  • The client vanishes halfway, leaving a pending row and orphaned multipart parts forever.
  • An object exists in the bucket that no row points to (row creation failed after signing, or the row was deleted).

Why not trust the client to say "I'm done"?

A client-driven POST /uploads/{id}/complete sounds natural but is unreliable: the app can be killed or lose connectivity between the last byte and the callback (so a finished upload stays pending), and a buggy or malicious client can claim success without uploading anything, or upload something different from what it declared. The only party that knows for certain that the bytes landed is the storage system itself.

The usual answer: event notifications and a status state machine

Create the row before issuing the URL with status = pending. Configure the bucket to emit an event notification (S3 ObjectCreated:*, including CompleteMultipartUpload) to SQS, SNS, EventBridge or a Lambda. A consumer looks up the row by the object key and moves it forward. Model it as a small state machine:

StatusMeaningMoves on when
pendingRow exists, URL issued, no bytes confirmedS3 event arrives (or the row expires)
uploadedStorage confirmed the object existsWorker picks it up for processing
processingScanning, thumbnailing, transcodingWorker finishes or fails
readySafe to show and downloadTerminal (or deleted later)
failed / expiredRejected, infected, or never completedCleanup job removes row and object

Making the consumer robust

  • At-least-once delivery, so be idempotent. S3 notifications can be delivered more than once and are not guaranteed to be ordered. Use a conditional update (UPDATE files SET status='uploaded' WHERE id=? AND status='pending') so a duplicate event is a no-op, and dedupe on object key plus version or sequencer where needed.
  • Verify, do not assume. The handler may HeadObject the key to confirm size and content type match what was declared, and reject or quarantine on mismatch.
  • A reconciliation job covers missed events. Events are reliable but not perfect (misconfiguration, consumer bug, downstream outage). Periodically scan pending rows older than the URL TTL plus a margin: if HeadObject finds the object, mark it uploaded (event was lost); if not, mark it expired and delete. In the other direction, list the bucket (S3 Inventory is cheaper than listing at scale) to find orphan objects with no row.
  • Lifecycle rules do the garbage collection. Configure AbortIncompleteMultipartUpload (for example after 1 to 7 days) and an expiration on a tmp/ or incoming/ prefix for unfinished uploads so abandoned data does not accumulate and bill you.
  • Optionally also let the client call "complete". That gives faster UX (the UI can move on immediately), but the server should verify against storage rather than trust the claim, and the event remains the authoritative signal.
Row first, URL second

Always insert the pending row before handing out the signed URL, never after. If you sign first and the insert then fails, the client can upload an object nobody knows about. If you insert first and signing fails, you merely have a harmless pending row that expires.

Step 4Downloads: CDN with signed URLs

Downloads go the same direction in reverse: keep bytes off your API tier. Once a file is ready, the API authorizes the user and returns a signed download URL; the client then fetches the bytes from a CDN (CloudFront, Cloudflare, Fastly, Cloud CDN) or, for rarely accessed private files, directly from S3 with a pre-signed GET. The CDN caches popular objects at the edge close to users and fetches from the bucket (the origin) only on a miss. See Scaling Reads for CDN caching mechanics.

  • Private vs public buckets. Truly public assets (marketing images, public avatars) can be served from a public or CDN-fronted bucket with long cache lifetimes and content-hashed names. Private user content should keep the bucket private and be reachable only through the CDN's identity (for CloudFront, Origin Access Control) plus signed URLs or signed cookies.
  • Signed URLs vs signed cookies. A signed URL grants one object; signed cookies grant access to a set of objects (for example all segments of a video) without rewriting every URL.
  • Range requests. HTTP Range: bytes=... returns 206 Partial Content. Both S3 and CDNs support it, which enables resuming a download, seeking inside a video, and parallel segmented downloads. Resumable downloads need no special server logic.
  • Streaming video. Rather than serving one huge MP4, transcode into many bitrates and cut into short segments (a few seconds each) listed in a manifest: HLS (.m3u8) or MPEG-DASH. The player fetches segments over plain HTTP from the CDN and switches bitrate to match bandwidth (adaptive bitrate). This is exactly why the post-upload processing step exists.
  • Set the right headers. Content-Type so browsers behave, Content-Disposition: attachment to force downloads for untrusted file types, and appropriate Cache-Control.
  • Short expiries and rotation. Signed download URLs for private content should expire quickly. For the CDN, the signing key pair is a secret that you rotate.

Step 5Post-processing, acceleration and deduplication

  • Hand off processing to async workers. After the ObjectCreated event, enqueue jobs for virus scanning, thumbnails, metadata extraction, transcoding to HLS renditions, OCR, and so on. This work is slow and bursty, so it belongs on a queue with workers that retry, not in a request path. See Long-Running Tasks, and Multi-Step Processes when it becomes a multi-stage pipeline.
  • Regional placement and transfer acceleration. Distance to the bucket hurts TCP throughput. Place buckets near your users, use multiple regions, or use S3 Transfer Acceleration (clients upload to the nearest edge location, which forwards over the provider's backbone). Treat it as a measured optimization, not a default.
  • Deduplication by content hash. For Dropbox-style products, split files into fixed or content-defined chunks (a few MB each), hash each chunk (for example SHA-256), and store chunks keyed by hash. Before uploading, the client sends the list of hashes and the server replies with which are missing, so identical chunks are never uploaded or stored twice (across versions of a file, and across users, subject to privacy and security considerations). It makes re-sync and small edits cheap: only changed chunks move. The cost is extra metadata, reference counting for garbage collection, and a hash-oracle privacy risk if cross-user dedup is exposed naively.

Trade-offs & pitfalls

Each improvement trades something away. The failures below are the ones a good interviewer will push on.

Two systems that must agree

Covered above: use a state machine, row-first ordering, events as the source of "uploaded", idempotent consumers, a reconciliation sweeper and lifecycle rules. Be explicit that the guarantee you are providing is eventual consistency with detection and repair, not atomicity.

Signed URL leakage and scope

The URL is a bearer credential. Mitigate: short TTL, narrow scope (one key, one method, pinned content type), HTTPS only, never log full URLs (query strings often end up in access logs and analytics), and treat a leaked upload URL as the ability to overwrite that single key until it expires. Rotate or restrict the signing identity to a minimal IAM policy (only s3:PutObject on the upload prefix). For one-shot semantics, new keys per upload prevent overwriting existing objects, and versioning protects against accidental overwrite.

Expiry vs very long uploads

The URL must be valid when the request starts; a request already in progress at expiry generally continues, but a retry after expiry fails. For multipart, sign one short-lived URL per part (or batches of them) and let the client request fresh ones as needed, rather than one long-lived mega-URL.

Untrusted content

  • Do not trust the declared type. The client chooses Content-Type and file name. Verify by sniffing magic bytes server-side after upload, and re-encode media (a transcoded image is far safer than the original).
  • Scan for malware. Common pattern: clients upload to an incoming/ (quarantine) prefix or bucket, a worker scans (ClamAV or a managed scanner), then promotes clean files to the serving location. Nothing is downloadable until status is ready.
  • Serve user content from a separate domain (for example usercontent.example.com or a distinct registrable domain), never your main one. Otherwise an uploaded HTML or SVG file executing in your origin can steal cookies or tokens (stored XSS). Add Content-Disposition: attachment and X-Content-Type-Options: nosniff for risky types.
  • Quotas and rate limits. Enforce per-user storage quotas and limit how many upload sessions can be issued per user, since signing is cheap for you but storage and egress are not. Cap declared sizes at issuance time.
  • Encrypt at rest (server-side encryption is default on most providers) and consider per-tenant keys for sensitive data.

Cost and operational gotchas

  • Orphan parts are invisible and billed. Always add the abort-incomplete lifecycle rule.
  • Request costs. Many small parts mean many PUT requests, each billed. Do not use a 1 MiB part size for 100 GiB files.
  • Egress is usually the dominant cost for downloads. A CDN generally lowers it versus serving from the bucket, and lets you set long cache lifetimes.
  • Browser CORS configuration on the bucket is a classic source of "it works in curl but not in the app" failures; allow the right origins, methods, and expose the ETag header so the client can read part ETags.
  • Hot prefixes are largely a non-issue on modern S3 (it scales request rates per prefix automatically), but random key prefixes (like a UUID) still avoid accidental hot spots and enumeration.

Progress and UX

Direct uploads mean your server does not see progress. The client knows its own byte counts, and the server learns about completion from events. For multi-device or processing progress ("transcoding 40%"), push status to the client with polling, SSE or WebSockets. See Real-Time Updates.

When NOT to use it

  • Small payloads. A 50 KB profile picture or a few-KB JSON blob does not justify pre-signed URL flows, events and sweepers. Accepting it via the API (with a strict size cap) is simpler and perfectly fine, as long as you cap sizes and do not allow it to grow into big files later.
  • You need to inspect or transform bytes synchronously before accepting. If a request must be rejected immediately based on content, direct-to-storage pushes validation after the fact. A bounded API-side upload (small files) or a staged flow is better.
  • Strong atomicity between metadata and blob is a hard requirement. Two systems cannot give you one transaction. If you truly need it for small items, consider storing them inside the database, or restructure so the database is the single source of truth and the blob is derivable.
  • Frequently edited, in-place file content (random writes inside a file, database files, shared mutable documents). Object stores replace whole objects. Use a filesystem or block storage, or a collaborative editing model built for it.
  • Low-latency small-record workloads. A key-value or relational store is the right home, not S3.

Interview script

Say it like this
"I do not want a 4 GB upload going through my API servers: it doubles bandwidth, holds a connection for tens of minutes, and a single dropped connection restarts everything. So I will store the bytes in object storage like S3 and keep only metadata in the database. The client asks my API for an upload, I create a row with status pending and return a pre-signed URL scoped to one server-chosen key with a short expiry. Deep-dive Q&A

Why not just have the client tell us when the upload is finished?

Because the client is the least reliable participant. The app may be killed between the last byte and the callback, leaving a finished upload stuck as pending. A buggy or malicious client may say "done" when nothing, or something different, was uploaded. The storage system is the only party that actually knows the object exists, so you subscribe to its event notification and update the database from that. A client "complete" call is still fine as a UX hint, as long as the server verifies it (for example with HeadObject) rather than believing it, and a sweeper repairs the cases where the event or callback never arrives.

A user is uploading 4 GB on flaky hotel Wi-Fi. Walk through how it survives disconnects.

The server initiates an S3 multipart upload and stores the UploadId in the metadata row. The client slices the file into parts (say 16 MiB), requests signed URLs for them, and uploads several in parallel, recording each returned ETag. If the network drops, in-flight parts fail and are retried with backoff; completed parts are safe in S3. After an app restart or a device change, the client asks the server for ListParts (or its saved state) to see which parts exist and uploads only the missing ones. When all parts are in, the server calls CompleteMultipartUpload with the ordered part list, S3 assembles the object, and the ObjectCreated event moves the row forward. Per-part checksums catch corrupted chunks, and an abort-incomplete lifecycle rule cleans up if the user never returns.

How do you stop someone from uploading 50 GB, or a malware executable, through a signed URL?

Layer the controls. At issuance, the user declares file size and type and you enforce quotas and caps before signing anything. For single-request uploads use a pre-signed POST with content-length-range and an exact content type condition; for multipart, you control how many parts you sign and their sizes. The URL is scoped to one server-chosen key and expires quickly. After upload, verify size and sniffed type via HeadObject and the first bytes, then scan in a quarantine prefix and only promote clean files to ready. Serve user content from a separate domain with nosniff and attachment disposition so that even a bad file cannot run in your origin. Rate-limit upload sessions per user.

The S3 event never arrives, or arrives twice. What happens?

Duplicates are expected (at-least-once delivery), so the handler is idempotent: a conditional update WHERE status='pending' turns the second delivery into a no-op, and any downstream job is keyed by file id so it is not enqueued twice. Missed events are repaired by a reconciliation job that finds pending rows older than the URL TTL plus a margin and calls HeadObject: if the object exists the row advances (the event was lost), if not the row is expired and deleted. A dead-letter queue on the consumer captures poison messages for inspection. Periodically, S3 Inventory is compared against the table to find orphan objects without rows.

How do you serve a private video securely and make it start fast?

Keep the bucket private and put a CDN in front, granting the CDN (and only the CDN) read access through an origin access identity. When an authorized user opens the video, the API returns a signed URL, or sets signed cookies so one authorization covers every segment. The video itself was transcoded after upload into several bitrates and cut into short HLS or DASH segments plus a manifest, so playback begins after fetching just the first segment and the player adapts bitrate to bandwidth. Popular segments are cached at the edge so most requests never reach S3. Keep signed-URL lifetimes short and rotate the CDN signing key.

Why not store files in the database, or on a network file system?

In a relational database, large values bloat tables, pollute the buffer pool, slow backups and replication, make the database the bandwidth bottleneck, and cost far more per GB, with no CDN integration. A network file system (NFS/EFS) gives you POSIX semantics you do not need, is pricier, scales less cheaply, and still routes bytes through your servers unless you build direct access. Object storage is built for exactly this: huge, immutable, cheap, durable, HTTP-addressable objects with signed access, lifecycle rules and event hooks. The one reason to reconsider is a very small, strongly-transactional blob where atomicity with a row matters more than scale.
