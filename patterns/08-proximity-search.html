Proximity Search

"Find the drivers near this rider." An ordinary database index sorts along one line, but a location is a point on a plane. A geospatial index cuts the map into regions so a query can discard almost the whole world before it examines a single row.

Geospatial index Geohash / quadtree / R-tree S2 & H3 Ride sharing & local search

TL;DR

Proximity search answers: "which items are within some distance of this point?" or "which are the K closest?". The core difficulty is that a normal index is one-dimensional, while "near" depends on latitude and longitude together. The fix is to turn two dimensions into something an index can handle by dividing the map into cells and indexing items by the cell they fall in. Climb this ladder and stop when it is good enough:

  1. Brute force / bounding box + exact distance. Fine for a few thousand rows.
  2. Grid or geohash. Encode a location as a string whose prefix identifies its cell; search your own cell plus its 8 neighbors, then filter by true distance.
  3. Quadtree or R-tree. Tree structures that adapt to density, so a crowded city is cut finely and an empty desert is not.
  4. S2 or H3. Hierarchical cell systems on a sphere, used by Google and Uber, with clean neighbor handling and multiple resolutions.

In practice you rarely build any of this yourself. PostGIS, Redis geo commands, Elasticsearch geo queries and MongoDB 2dsphere indexes give it to you. The design decisions that remain are about the shape of your data: places that almost never move (Yelp) versus things that move constantly (Uber drivers), and what you combine the distance search with (filters, ranking, ETA).

Recognize it when…
  • The prompt says "nearby", "within N miles", "closest", "around me" or "in this area".
  • You are designing Uber, Lyft, DoorDash, GoPuff, Yelp, Google Maps places, Tinder, Airbnb map search, or "find a store".
  • Every query carries a location, and the answer set is a tiny fraction of all the data.
  • Items have coordinates and the main filter is distance, often together with other filters (open now, category, rating).

The problem

Suppose you store restaurants in a table with lat and lon columns and a user asks for restaurants within 2 miles. You have no good way to ask the database that question quickly. To see why, recall what an index is.

Why a normal index fails

A B-tree keeps keys in a single sorted order. It answers "give me everything between A and B" extremely well, but only along that one ordering. "Near me" is a two-dimensional question: a circle on the map.

  • Index on lat alone. WHERE lat BETWEEN 37.76 AND 37.79 returns every row in a horizontal band around the whole planet at that latitude. A band 3 km tall circles the globe and contains cities in every longitude. The index narrowed one dimension and did nothing for the other, so the database still examines (and then discards) the vast majority of the band.
  • Composite index on (lat, lon). This sorts by latitude first, then longitude within equal latitudes. Because latitude is a continuous value, nearly every row has a unique latitude, so the longitude part is almost never used to narrow the range. It behaves like the single-column index. (This is the leftmost-prefix rule from Scaling Reads: only the first column of a range predicate can seek.)
  • Two separate indexes (one on lat, one on lon) means the planner fetches two huge sets and intersects them. Better than nothing, but each set is still a whole band or a whole meridian strip.
  • Sorting by distance (ORDER BY distance LIMIT 10) cannot use any of these indexes at all, because distance to this user is a computed value that no pre-sorted index contains. The database must compute it for every candidate row.

The numbers that make this hurt

Uber-scale data makes the naive approach untenable: millions of drivers, each of whose positions changes every few seconds, and millions of "who is nearby?" queries per day, each needing an answer in tens of milliseconds. A full scan per query, or a band scan that touches millions of rows, is impossible. We need an index whose query cost depends on how many results are nearby, not on how many rows exist worldwide.

The one-sentence insight

"A B-tree sorts along one axis, but proximity is two-dimensional, so I'll use a geospatial index that partitions the map into cells; a query then examines only the few cells around the user instead of the whole world."

When it comes up

It appears whenever location is the main way users look for things:

  • Uber / Lyft: find available drivers near a rider. Locations change every few seconds.
  • DoorDash / Uber Eats / GoPuff: find restaurants or the warehouse that can serve an address; then find couriers near the pickup.
  • Yelp / Google Maps places: "restaurants within 2 miles", usually combined with category, rating and "open now". Places rarely move.
  • Tinder / Bumble / Nextdoor: people within N km. Positions are semi-static and privacy-sensitive.
  • Airbnb / Zillow / real-estate map search: listings inside the visible map rectangle (a bounding-box query, not a circle).
  • Store locators, ATM finders, EV charger maps, geofencing, "weather alerts for my area".

Two flavors are worth distinguishing early, because they lead to different designs:

  • Static or slowly changing places (restaurants, stores, listings): read-heavy, write rarely. Index once, cache aggressively.
  • Highly dynamic objects (drivers, couriers, friends): write-heavy position updates plus read queries. The index has to absorb constant updates.

Solutions, in escalation order

As always, start with the cheapest approach that could work. The ladder below goes from "no index at all" to the cell systems used by Google and Uber. Every rung exists to answer one question: how do I look at fewer candidates?

Step 0Brute force, or bounding box plus exact distance

Do not underestimate this. If you have a few thousand rows, compute the distance to every one and sort. The work is trivial and there is nothing to build or maintain. Even for larger tables, a cheap bounding-box prefilter can reduce what you must compute exactly.

Degrees are not distances

Latitude and longitude are angles, not meters, and the conversion is not uniform:

  • One degree of latitude is about 111 km everywhere (about 69 miles).
  • One degree of longitude is about 111 km times cos(latitude): roughly 111 km at the equator, about 88 km at 37 degrees north (San Francisco), about 55 km at 60 degrees north, and zero at the poles, where all meridians meet.

Consequently a "0.02 degree" box is a different physical shape in different places, and plain Euclidean distance on raw degrees is wrong. For a radius of r km around (lat0, lon0), the box half-sizes are dlat = r / 111 and dlon = r / (111 * cos(lat0)).

The haversine formula

The great-circle distance between two points on a sphere (the shortest path over the surface) is given by the haversine formula, where phi is latitude, lambda is longitude (both in radians) and R is Earth's radius, about 6,371 km:

a = sin^2((phi2 - phi1) / 2)
    + cos(phi1) * cos(phi2) * sin^2((lambda2 - lambda1) / 2)
d = 2 * R * asin( sqrt(a) )

Treating the Earth as a perfect sphere introduces an error of up to roughly 0.3 percent compared with the true ellipsoid, which is irrelevant for "nearby" features. (PostGIS geography uses a spheroid for more accuracy; Redis uses a haversine variant.)

In SQL

-- :dlat = r / 111.0      :dlon = r / (111.0 * cos(radians(:lat)))   (computed in the app)
SELECT id, name,
       2 * 6371 * asin(sqrt(
         power(sin(radians(lat - :lat) / 2), 2) +
         cos(radians(:lat)) * cos(radians(lat)) *
         power(sin(radians(lon - :lon) / 2), 2)
       )) AS km
FROM   places
WHERE  lat BETWEEN :lat - :dlat AND :lat + :dlat   -- cheap prefilter
  AND  lon BETWEEN :lon - :dlon AND :lon + :dlon
ORDER  BY km
LIMIT  20;

An index on lat helps the prefilter, but as shown earlier it still reads a whole latitude band. At a few thousand rows this is instant. At tens of millions it is not, which is the signal to move up the ladder. Note also that a box that crosses longitude 180 (the antimeridian) must be split into two ranges.

Step 1Grid and geohash

The simplest spatial index is a grid: slice the map into fixed-size squares, and give every square an id. Store each item's cell id in an ordinary indexed column. To find things near a point, compute the point's cell id, look up that cell (and its neighbors), then filter by exact distance. Now a normal B-tree on cell_id does the heavy lifting, because "which cell?" is a one-dimensional equality lookup.

Geohash is the best-known way to name grid cells, and it is hierarchical.

How geohash works

  1. Start with the whole world: latitude in [-90, 90], longitude in [-180, 180].
  2. Repeatedly bisect, alternating between longitude and latitude (longitude first). Each bisection produces one bit: 1 if the point is in the upper half of the current range, 0 if in the lower half. The range then shrinks to that half.
  3. The bits from both axes are interleaved (lon, lat, lon, lat, ...) into one bit string.
  4. Every 5 bits are encoded as one character of a 32-symbol alphabet (base32: digits and lowercase letters, omitting a, i, l, o). The result is a short string such as 9q8yy, which is roughly downtown San Francisco.

Two properties make it useful:

  • A prefix is the containing cell. 9q8y is a bigger cell that contains 9q8yy, which contains 9q8yyk. Each extra character divides the cell into 32 smaller ones (an 8 by 4 or 4 by 8 sub-grid).
  • Longer string means smaller cell, i.e. higher precision. Approximate cell sizes (at the equator; cells get narrower in east-west width as you move toward the poles, and exact figures vary by source):
Geohash lengthApprox. cell size (width x height)Typical use
4~39 km x 20 kmCity-region scale
5~5 km x 5 kmNeighborhood-to-city search for a "within a few km" query
6~1.2 km x 0.6 kmWalking-distance search, ride-sharing pickup zones
7~150 m x 150 mCity block, fine-grained supply counts
8~40 m x 20 mBuilding-level

Because the code is just a string, you can store it in any database and use a plain B-tree: WHERE geohash LIKE '9q8yy%' is a prefix range scan, which a B-tree handles well. You can also store several precisions (gh4, gh5, gh6) as separate columns and pick the one that matches the search radius.

The boundary problem: why you need the neighbors

A point near the edge of its cell can be very close to a point in the adjacent cell, yet share no useful prefix with it. Two people 10 meters apart on either side of a cell boundary can have totally different geohashes. The worse case is the major boundaries (the equator or the prime meridian), where neighboring cells differ in their very first character. So looking only at your own cell silently misses nearby results.

This is also a symptom of the Z-order discontinuity: geohash orders cells along a Z-shaped curve that sometimes jumps across the map. Closeness in string-prefix terms implies closeness in space, but not the other way around.

The standard remedy is: choose a cell size comparable to (or somewhat larger than) the search radius, then query your own cell plus its 8 neighbors (a 3 by 3 block), and finally filter the candidates by exact distance. The grid is a cheap candidate generator; the haversine check removes the corners that fall outside the true circle.

Pros

  • Trivial to understand and implement
  • Works in any database, even a key-value store, with a normal index
  • Hierarchical: choose precision to match the radius
  • Cheap, constant-time insert and update (just recompute a string)
  • Easy to shard on (prefix = natural partition key)

Cons

  • Boundary problem: you must query neighbors
  • Cells are rectangles whose real size changes with latitude, and distortion near the poles
  • Fixed cell size ignores density: a Manhattan cell is full, a Montana cell is empty
  • Prefix discontinuities; Z-order curve is not locality-perfect
  • Poor fit for polygons and non-point shapes

Step 2Quadtree and R-tree: adapt to density

A uniform grid wastes effort. Manhattan has thousands of drivers per square kilometer; rural Montana has a few per thousand. A fixed cell size is either far too coarse downtown (huge candidate lists) or far too fine in the countryside (millions of empty cells). Tree-shaped indexes fix this by subdividing only where the data is dense.

Quadtree

A quadtree recursively splits a square region into four equal quadrants (NW, NE, SW, SE).

  1. Start with one node covering the whole area, which holds points directly.
  2. Choose a capacity threshold, for example 50 points per leaf.
  3. When inserting would push a leaf above capacity, split it into four children and redistribute its points.
  4. Repeat. Crowded areas end up deep in the tree with small leaves; empty areas stay as large leaves.
  5. Query: start at the root and descend only into children whose rectangle intersects the search circle (or box). Collect points from the leaves reached, then filter by exact distance. To get the nearest K, visit nearer children first and prune any child farther away than the current K-th best.

Pros

  • Adapts to density automatically; each leaf has a bounded number of points
  • Natural nearest-neighbor search with pruning
  • Simple, fast, and great as an in-memory structure

Cons

  • Usually lives in application memory, not in a standard database; you must persist, rebuild and replicate it yourself
  • Moving objects require delete + insert, and heavy churn needs rebalancing or periodic rebuilds
  • Hard to distribute: a tree has one root, so you shard by region and keep one tree per shard
  • Can become deep and unbalanced with clustered data

R-tree and GiST: what databases actually use

An R-tree is the disk-friendly cousin of the quadtree, and it is the structure behind PostGIS indexes. Instead of dividing space into fixed quadrants, it groups nearby objects into minimum bounding rectangles (MBRs), then groups those rectangles into larger rectangles, and so on, forming a balanced tree shaped like a B-tree:

  • Leaf entries store the bounding box of each object (a point is a degenerate box; a polygon is its bounding box).
  • Internal nodes store the box that encloses all their children, plus pointers.
  • Search: start at the root and descend into every child whose rectangle intersects the query region. Unlike a quadtree, sibling rectangles may overlap, so a query can have to follow more than one branch.
  • Nodes are sized to fit disk pages, and insert, delete and node-splitting are handled incrementally, so it is a good fit for a transactional database.

In PostgreSQL, CREATE INDEX ... USING GIST (geom) builds such an R-tree-style index via the GiST (Generalized Search Tree) framework. It supports points, lines and polygons, so you can ask "which delivery zone polygon contains this address?" as well as "what is within 2 km?". MySQL spatial indexes and SQLite's R*Tree module work on the same principle.

Quadtree vs R-tree in one line

A quadtree divides space (fixed quadrants, regardless of where the points are); an R-tree groups objects (rectangles that tightly wrap whatever is there). Quadtrees are simpler and in-memory; R-trees are balanced, disk-based and handle shapes.

Step 3Google S2 and Uber H3: cells on a sphere

Geohash treats latitude and longitude as a flat rectangle, which distorts badly near the poles and ignores that the Earth is a sphere. Two modern libraries solve this by building the cell system directly on the sphere. Both are hierarchical grids with 64-bit integer ids, and they are what large systems use when they need more than a database offers.

S2 (Google)

  • Structure: project the sphere onto the six faces of a cube, subdivide each face as a quadtree (up to 30 levels), and number the cells along a Hilbert space-filling curve. The smallest cells are around a square centimeter; level choice trades size for count.
  • Cell id: a 64-bit integer. The Hilbert curve has much better locality than geohash's Z-order: cells that are close in id are close in space, with far fewer jumps. So a region maps to a small number of contiguous id ranges, which a plain sorted index (B-tree, LSM, Bigtable) scans efficiently.
  • Covering: to search a region, S2's region coverer picks a small set of cells (possibly at mixed levels) that together cover it; you then query each cell's id range and filter exactly. The same idea works for circles, rectangles and polygons.
  • Used inside Google products, and historically underlies MongoDB's 2dsphere indexes and several other systems.

H3 (Uber)

  • Structure: the globe is tiled with hexagons (plus exactly 12 pentagons at each resolution, a topological necessity), at 16 resolutions (0 to 15). Each finer resolution subdivides a cell into about 7 children. Cell edge lengths range from thousands of kilometers at resolution 0 to well under a meter at 15; resolution 8 is on the order of a few hundred meters per edge and resolution 9 a bit over 100 meters (approximate figures).
  • Cell id: a 64-bit integer. Neighbor and radius operations are library calls: grid_disk(cell, k) returns the cell plus all cells within k steps; latlng_to_cell(lat, lng, res) maps a point to its cell.
  • Why hexagons? In a square grid a cell has 4 edge-neighbors at distance 1 but 4 corner-neighbors at distance about 1.41, so "neighbor" is ambiguous. Every hexagon has 6 neighbors, all equidistant from its center and all sharing an edge. That uniformity makes "cells within k steps" approximate a circle much better than a square block does, and it makes smoothing, gradients and "move to adjacent cell" logic simpler. Uber uses H3 for demand and supply aggregation, surge pricing, marketplace analytics and matching.
  • Trade-off: hexagons do not nest perfectly (a child hexagon is not exactly contained in its parent), so hierarchy is approximate, and hex cells are more awkward for exact region containment than S2's strict squares.

Putting it together: the real-world architecture

Choosing between geohash, quadtree and S2 is the easy part. The architecture depends on how often locations change.

Static places: Yelp, store locators, listings

Restaurants open and close rarely, so the data is read-heavy and nearly write-free. This is the easy case.

  • Store it in a database with a built-in spatial index: PostgreSQL with PostGIS (GiST index), or Elasticsearch/OpenSearch with a geo_point field. Both give you distance filtering and sorting directly.
  • Search plus filters: real queries are "Thai, open now, 4+ stars, within 2 miles, sorted by relevance". Elasticsearch is attractive because it combines a geo filter with text search, term filters and ranking in one request. In Postgres you combine the spatial predicate with ordinary column filters and indexes.
  • Precompute and cache: because the data barely changes, you can precompute a cell-to-places mapping (for example place ids per geohash-6 or H3 cell), and cache popular area queries (a query at a coarse cell and category is shared by many users). See Scaling Reads. Snap the user's coordinates to a cell before building the cache key; otherwise every user has a unique key and the hit rate is zero.
  • Scale reads with replicas; writes (a new restaurant) are trivial.
-- PostGIS: a geography column + GiST index, then ST_DWithin
CREATE EXTENSION IF NOT EXISTS postgis;
ALTER TABLE places ADD COLUMN geog geography(Point, 4326);
UPDATE places SET geog = ST_SetSRID(ST_MakePoint(lon, lat), 4326)::geography;  -- note: lon first
CREATE INDEX idx_places_geog ON places USING GIST (geog);

SELECT id, name,
       ST_Distance(geog, ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)::geography) AS meters
FROM   places
WHERE  ST_DWithin(geog, ST_SetSRID(ST_MakePoint(-122.4194, 37.7749), 4326)::geography, 3200)  -- meters, about 2 miles
  AND  category = 'thai' AND is_open
ORDER  BY meters
LIMIT  20;

Two details worth knowing: with the geography type, distances are in meters on a spheroid, and ST_DWithin is index-aware (it first uses the GiST index on bounding boxes, then checks exact distance). The older ST_Distance(...) < r form cannot use the index. PostGIS takes coordinates as (longitude, latitude), x then y, which trips up many people.

Highly dynamic locations: Uber drivers

Now the points move. Each driver app sends a location ping every few seconds. Only the latest position matters to matching; old positions are history for a different system.

The write volume

A hedged back-of-envelope: 1 million online drivers pinging every 4 seconds is 1,000,000 / 4 = about 250,000 location writes per second (peak-hour global numbers will differ). That is far beyond what you want to push through a transactional relational database with a disk-based spatial index, where every update rewrites index entries. It is, however, comfortable for in-memory stores spread across a number of shards.

Design

  • Keep only the latest position, in memory. Use Redis geo commands (GEOADD overwrites a member's position), or your own cell_id -> set of driver ids map plus driver_id -> (cell_id, lat, lon, timestamp). When a driver moves, you compute their new cell; if it equals the old cell, just update the coordinates; if not, remove from the old cell's set and add to the new one.
  • Expire stale drivers. If a phone loses signal or the app is killed, the driver must disappear from results. Attach a timestamp to each ping and treat anything older than, say, 10 to 30 seconds as gone. Redis geo sets (which are sorted sets) have no per-member TTL, so common patterns are a per-cell key with an expiry that is refreshed by each ping, or a companion sorted set scored by last-seen time that a background job trims.
  • Shard by geography. Positions in different cities never interact, so partition by city, region or top-level cell (an H3 or geohash prefix). Each shard handles a fraction of the writes and holds a small index. This is exactly the "partition by a natural key" idea from Scaling Writes.
  • Reduce the write rate. Batch pings from the same gateway, send updates only when the driver has moved more than some distance, slow down the ping rate when idle or stationary, and drop out-of-order pings. These are the batching and write-reduction tactics from Scaling Writes.
  • Separate history from the live index. Stream every ping into a log (Kafka) for trip reconstruction, analytics and ML, with a consumer that updates the live index. Matching reads from the in-memory index only.
  • Durability is optional. The live index is rebuildable: if a shard restarts, drivers re-ping within seconds. Do not pay for strong durability on data that is obsolete in 5 seconds.
# Redis: store and query live driver positions (Redis 6.2+ for GEOSEARCH)
GEOADD drivers:sf  -122.4194 37.7749  driver:42      # longitude first, then latitude
GEOADD drivers:sf  -122.4101 37.7810  driver:77

GEOSEARCH drivers:sf  FROMLONLAT -122.4180 37.7760  BYRADIUS 2 km  ASC  COUNT 20  WITHDIST

# Redis stores each member in a sorted set, using a 52-bit geohash as the score.
# One key per city/region gives you sharding and bounded key sizes.

Ranking, filters, radius and pagination

  • Distance is not ETA. The nearest driver in a straight line may be across a river, on the other side of a one-way street or stuck in traffic. The usual pattern is two-phase: a fast geo query returns the nearest N (say 20 to 50) candidates, then a routing engine (OSRM, Valhalla, Google or Mapbox matrix APIs, or an in-house service) computes real driving ETAs for just those, and you rank by ETA (plus other signals like rating or acceptance rate). Do not call the routing engine for every driver in the city.
  • Combine with filters. Filter on category, "open now", rating, price, vehicle type. In Elasticsearch you put the geo clause and the filters in one bool query. In a cell-based design you fetch candidates from the cells and apply the filters in memory, or keep a separate index per filter value for the most common cases (for example one geo set per vehicle type).
  • Radius expansion. If the 3x3 block yields too few results (or none), widen the search: add the next ring of cells, or move up one precision level, and repeat up to a maximum radius. This is a loop, not a single query: start tight for low latency and expand only when needed.
  • Pagination. "Page 2 of results by distance" over a moving set is tricky. For static places use a cursor of (distance, id) so ties are stable. For drivers, nobody pages; take the top N and stop.

Edge cases

  • Dense city centers. A single geohash-6 cell may hold thousands of points. Use a finer precision there (or a quadtree/H3 at a finer resolution). Adaptive structures were invented for this.
  • Shard boundaries. If you shard by city or cell, a rider at the edge of one shard is near drivers in the next. Query the neighbor shards too (the same "own cell plus neighbors" logic, one level up), or assign points near a boundary to both shards.
  • Antimeridian and poles. Longitude wraps at plus or minus 180 degrees, so a naive "lon between a and b" box splits into two ranges near Fiji and the Aleutians. Near the poles longitude lines converge and rectangular cells become very distorted. S2 and H3 handle both cleanly; hand-rolled geohash code often does not. (Most products simply do not operate there.)
  • GPS noise and staleness. Positions are accurate to several meters at best and can jump. Do not trust a position older than your TTL.
  • Privacy. Precise location is sensitive personal data. Show riders a fuzzed or rounded driver position until pickup, do not expose exact coordinates of other users in dating and social apps (round to a cell or return only a distance bucket such as "2 km away"), limit retention of history, and lock down access to the location store.

Trade-offs & pitfalls

The interesting questions are not "which tree" but what each choice costs you.

Cell size is a precision versus work trade-off

Large cells mean few cells to look up but many candidates to filter; small cells mean tight candidate sets but many cells to cover a given radius (and more empty lookups). A rule of thumb for grid designs: pick a cell about the size of the typical search radius, so the 3x3 block covers the circle with a modest amount of waste. If radii vary a lot (500 m to 50 km), store several resolutions, or use S2 or H3 where changing the level is built in.

Candidates then exact filter: two-phase queries

Every approach in this page is a filter-then-refine pipeline. The index returns a superset (the cells' contents); you then compute exact distance and discard false positives. Forgetting the refine step returns results that are "in the right cells" but outside the radius, especially at the corners of the 3x3 block.

Write amplification and index churn

A disk-based spatial index (PostGIS GiST, MySQL spatial) pays for every update: it must remove the old entry and insert a new one, potentially splitting pages. At a few writes per second per object across millions of objects, that is the bottleneck, not the search. This is why live-moving data usually sits in memory, and the durable database holds only the slow-changing facts.

Hot cells

An airport, a stadium after a concert, or a city center on New Year's Eve concentrates both queries and writes into one cell, and thus one shard. Mitigate with finer cells at hot spots, splitting a hot shard by sub-cell, caching results with a short TTL, and, for supply counting, approximate or sampled counts rather than exact lists.

Consistency of the moving index

The index is always slightly behind reality: a driver may have accepted another trip or driven away since their last ping. Matching therefore has to confirm availability at the moment of assignment (see Dealing with Contention, which covers claiming a driver so two riders do not get the same one). Treat the geo index as a hint, not the truth.

Cross-shard queries

Sharding by region is great until the query sits on a boundary. Handle it by also querying adjacent shards for riders within one search radius of the boundary. Pick shard boundaries where little traffic crosses them (along rivers, mountains, sparsely populated areas), not through the middle of a city.

Choosing the structure

  • Need SQL plus polygons plus transactions: PostGIS (R-tree/GiST).
  • Need geo plus text search and filters: Elasticsearch/OpenSearch.
  • Need fast, simple, in-memory moving points: Redis geo or a cell-to-set map.
  • Need to partition a huge key-value store by location: geohash or H3 cell as a partition key.
  • Need global scale with multiple resolutions: S2 or H3.

When NOT to use it

  • Small data sets. With a few thousand rows (a thousand restaurants, a few hundred store locations) a plain scan with a haversine calculation is microseconds to a few milliseconds and needs no index. Building and maintaining a spatial index is extra complexity and, at this size, can even be slower than just scanning memory. Measure before adding it.
  • Don't build your own geo index. Writing a quadtree or a geohash library for production is a trap: boundary bugs, antimeridian and pole cases, precision errors and rebalancing are all solved problems. Use PostGIS, Redis, Elasticsearch, S2 or H3. Whiteboarding a quadtree to explain how it works is great; proposing to run a custom one is not.
  • The question is not spatial. "All stores in the state of California" or "orders from the Berlin region" is a plain equality or foreign-key lookup (store a region id). You do not need geometry to filter by an administrative area.
  • The bottleneck is elsewhere. If the real problem is a huge volume of pings, that is a write-scaling problem first (see Scaling Writes); if it is repeated identical area searches, that is a caching problem (Scaling Reads).
  • You need exact route distance for every candidate. Geo indexes give straight-line distance. Road-network distance needs a routing engine; do not try to emulate it with cells.

Interview script

Say it like this
"Finding nearby drivers is a two-dimensional query, and a normal B-tree only sorts along one axis, so a latitude range gives me a band around the whole planet. I need a geospatial index. I'd divide the map into cells, using geohash, H3 or S2, so a query takes the rider's cell plus its neighbors and then filters by exact distance. I wouldn't build that myself. For places like restaurants, which rarely change, I'd use PostGIS or Elasticsearch with a geo index and cache popular area queries. Drivers are different: with a million drivers pinging every four seconds that is about 250K writes per second, so I'd keep only the latest position in memory in something like Redis, sharded by city, with a TTL so stale drivers drop out. A geo search returns the nearest few dozen candidates, then a routing service ranks them by real ETA. And if we only had a thousand rows, I'd skip the index and scan."

Deep-dive Q&A

Why can't I just put a composite index on (lat, lon)?

A composite B-tree sorts by latitude first and only uses longitude to break ties between identical latitudes, which almost never happen with real coordinates. A range predicate on the first column can seek, but the second column then just filters. So the index narrows latitude to a band that wraps around the globe, and the database still scans every row in that band. A spatial index (R-tree, or a cell id from geohash, S2 or H3) maps two dimensions onto something searchable so both axes narrow at once.

Explain the geohash boundary problem and how you solve it.

Two points either side of a cell boundary can be a few meters apart yet have different geohashes, sometimes differing from the first character (the equator, the prime meridian). A query that looks only at the user's own cell misses them. The fix is to query the user's cell plus its 8 neighbors, with cells at least as large as the search radius, and then compute the exact distance to filter the candidates. The deeper cause is that the Z-order curve is not locality-preserving: prefix similarity implies closeness but not the reverse. S2's Hilbert curve reduces the discontinuities, and H3's hexagons make "the neighbors" uniform.

Geohash, quadtree, R-tree, S2, H3: when would you pick each?

Geohash when you need something trivial that works in any database or key-value store and you can live with neighbor queries. Quadtree for an in-memory matching service where density varies a lot and you can hold one tree per shard. R-tree/GiST when you want it inside a transactional SQL database with polygons and rich queries, which is just PostGIS. S2 for global, multi-resolution, region-covering workloads and range scans over integer ids. H3 when you care about uniform neighbors, aggregation and analytics (surge pricing, supply/demand heatmaps) with hexagon cells. In an interview, the key is to explain the trade-off and then say "I'd use the one my database provides".

Drivers ping every 4 seconds. How do you design the location store?

Compute the load first: 1M drivers / 4s is about 250K writes per second. Keep only the latest position, in memory (Redis geo or a custom cell-to-driver map), shard by city or top-level cell so each shard handles a fraction, and give entries a short TTL so offline drivers vanish. Reduce traffic by batching at gateways and by sending pings only on meaningful movement. Stream all pings to a log for history and analytics separately. The index is reconstructible from the next round of pings, so it does not need heavy durability. Matching reads from the index, then confirms availability atomically when it assigns a driver.

Nearest by distance is not the best driver. What do you do?

Use the geo index only to generate candidates (the nearest 20 to 50 by straight line), then call a routing engine for road-network ETA on that short list and rank by ETA, adjusted for factors like acceptance rate or vehicle type. This keeps the expensive routing calls to a handful per request. If the candidate list is too small (few drivers nearby), expand the search ring and repeat up to a maximum radius.

A user searches near a shard boundary or the antimeridian. What breaks?

Near a shard boundary, relevant points live on the neighboring shard, so you must query adjacent shards (or duplicate boundary points into both). Near longitude 180 a naive "lon between a and b" bounding box wraps around, so it must be split into two ranges; geohash-based neighbor code can also break there, whereas S2 and H3 are defined on the sphere and handle the wrap-around. Near the poles, rectangular cells become distorted and longitude shrinks to zero, which is again a reason to prefer sphere-native cell systems if you ever need such regions.
