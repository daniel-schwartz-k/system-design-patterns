Multi-Step Processes

One user click can trigger a chain of work across several services, third-party APIs and even a human in a warehouse, lasting hours or days. No single database transaction can cover that, so you need a way to make the whole chain survive crashes, retries and partial failures.

Saga Workflow engines Idempotency Compensation

TL;DR

When a feature needs several services (and sometimes people) to cooperate over a long time, you cannot wrap it in one ACID transaction. Instead you split it into steps, make every step individually reliable, and define what "undo" means if a later step fails. Climb this ladder and stop as soon as the problem is solved:

  1. Hand-rolled state machine: a status column, a cron job and retry code. Fine for two or three steps inside one service, and it rots quickly beyond that.
  2. The saga pattern: a sequence of local transactions, each paired with a compensating transaction that semantically undoes it. Coordinated either by a central orchestrator or by services reacting to each other's events (choreography).
  3. A durable workflow engine (Temporal, AWS Step Functions, Azure Durable Functions, Conductor, Camunda): you write the flow as ordinary code or a state-machine definition, the engine persists every completed step, and after a crash the workflow resumes exactly where it stopped, with retries, timers and a full history for free.

Underneath all three sits the same toolkit: idempotency keys (so a retry never charges the card twice), timeouts, and the transactional outbox (so state changes and the messages announcing them never diverge).

Recognize it when…
  • One request fans out into several services or third-party APIs (payments, shipping, email, KYC).
  • The flow includes a human step or an external callback: warehouse pick, manual approval, driver acceptance.
  • It can take minutes, hours or days, so you cannot hold a connection or a lock open.
  • The prompt says "if step N fails, we have to undo steps 1 to N-1", or "what if the server crashes in the middle?"
  • Typical nouns: checkout, order fulfilment, booking, onboarding, loan approval, ride dispatch, money transfer.

The problem

Take an online store. Behind a single "Buy" click the system must: reserve the inventory, charge the card, create a shipping label, wait for someone in a warehouse to physically pick the item off a shelf, and finally send a confirmation. That is at least four services, two of which are third-party APIs, plus a human. It can take days.

Why one ACID transaction is impossible

  • Each service owns its database. In a microservice architecture the inventory, payments and shipping services have separate datastores. A BEGIN ... COMMIT only spans one database.
  • Third-party systems don't join your transaction. Stripe, a carrier API or an email provider cannot be "rolled back" by your database; they expose ordinary HTTP calls with their own side effects.
  • Humans and clocks. A transaction that waits two days for a warehouse worker would hold locks for two days. Databases are built for transactions measured in milliseconds.
  • Availability. Coordinating many independent systems atomically means the whole operation is only as available as the worst participant.

If you solve this by hand, with status columns, cron jobs and retry logic scattered across five services, nobody can answer "where is order 8123 right now?" and the on-call engineer inherits a mess. The pattern is about replacing that scatter with something explicit, durable and observable.

When it comes up

It shows up whenever a design includes money, physical goods, or more than one team's services. Typical prompts:

  • E-commerce checkout / order fulfilment: the running example on this page.
  • Ticketing and booking (Ticketmaster, Airbnb, flights): hold a seat, take payment, issue the ticket, release the hold on failure.
  • Payments and money transfer: debit one account, credit another, notify, reconcile.
  • Ride-hailing / food delivery: match, driver accepts (human), pick up, drop off, charge.
  • Media pipelines (YouTube-style): upload, transcode, moderate, publish. See Handling Large Blobs.
  • Onboarding, KYC and approvals: multi-day flows with documents, reviewers and reminders.

Solutions, in escalation order

Start with the simplest thing that keeps you correct. Each step below buys more reliability and visibility at the price of more machinery, so don't jump to a workflow engine for a two-step flow, and don't hand-roll a six-step flow that spans days.

StepTechniqueReach for it when…Main cost

Note that steps 2 and 3 are not alternatives so much as layers: a workflow engine is essentially a saga orchestrator you don't have to build yourself. The saga is the design; the engine is a way to run it reliably.

Step 1Hand-rolled state machine

The natural first attempt: add a status column to the orders table (PENDING, PAID, RESERVED, SHIPPED, ...). The code that handles each step updates the status after it succeeds. A cron job periodically scans for orders stuck in an intermediate status and retries them. Retries use a retry_count column and some backoff.

-- Every few minutes, a cron job does something like this:
SELECT id FROM orders
WHERE status = 'PAID'
  AND updated_at < now() - interval '10 minutes'
  AND retry_count < 5;
-- ...then re-calls the shipping service for each one.

For a short flow inside one service, this is perfectly reasonable, and you should not be embarrassed to say so in an interview. A well-modelled state machine (explicit allowed transitions, row-level locking or a version column, idempotent handlers) is the seed of everything that follows.

Why it rots

  • State is scattered. Each service has its own status column, cron job and retry logic. The "real" state of an order is the combination of five tables.
  • Crash windows everywhere. Between "call the payment API" and "write status = PAID" there is a gap. If the process dies in it, the cron job will charge again unless every call is carefully idempotent.
  • Retry logic is re-invented per call. Backoff, jitter, max attempts, dead-lettering: each one is written (and gets bugs) many times.
  • Timers are painful. "Cancel the order if the warehouse hasn't picked it within 3 days" turns into yet another cron query and another column.
  • No history. You see the current status, not what happened. Debugging "why was this customer double charged?" means digging through logs of five services.
  • Compensation is ad hoc. Undo logic lives wherever someone remembered to put it.

Pros

  • No new infrastructure
  • Easy to understand for 2 or 3 steps
  • Fine when everything is in one database (then use one transaction)

Cons

  • Reliability logic duplicated and bug-prone
  • Hard to observe, hard to change safely
  • Timers, human steps and compensation are all bolt-ons
  • The on-call engineer pays the bill

Step 2The Saga pattern: why and how

1. Why it exists: the problem with two-phase commit

The textbook answer to "make several databases commit atomically" is two-phase commit (2PC). A coordinator asks every participant to prepare (do the work, write it durably, hold the locks, and promise it can commit). If all say yes, the coordinator tells everyone to commit; if any says no, everyone aborts. It gives true atomicity, and it is exactly what you do not want across microservices:

  • Locks are held across services for the whole protocol. Any other transaction touching those rows waits.
  • It blocks if the coordinator dies after participants have prepared: they are "in doubt", holding locks, and cannot decide alone.
  • Many participants can't do it. Third-party APIs, SaaS products, most NoSQL stores and message brokers don't support XA/2PC at all.
  • Availability and latency suffer. The operation needs every participant up, and latency is the sum of two round trips to the slowest one.
  • It doesn't fit long-running or human steps. You can't hold locks for three days.

A saga (Garcia-Molina and Salem, 1987, originally for long-lived database transactions) takes the opposite trade. It is a sequence of local transactions: each service commits its own change to its own database immediately, then triggers the next step through a message or call. Since earlier steps are already committed, a failure later on cannot roll them back. Instead the saga runs compensating transactions that semantically undo what was done. You give up all-or-nothing isolation in exchange for availability, autonomy and the ability to run for days.

2. How it works: the store example

Break the order into four local transactions, each (except the last) with a compensation:

Local transactionServiceCompensation
T1 Reserve inventoryInventoryC1 Release the reservation
T2 Charge cardPaymentsC2 Refund the charge
T3 Create shipping labelShippingC3 Void the label
T4 Notify customerNotificationsNone needed: retriable, and a failure here must not undo the order

Happy path. Each step commits locally and hands off to the next. Nothing is ever rolled back; if everything succeeds, the compensations are simply never used.

Failure at T3. Suppose the shipping provider is down for longer than the retry budget. T1 and T2 have already committed, so we cannot roll them back. Instead the saga runs the compensations for the completed steps, in reverse order: first C2 (refund the card), then C1 (release the stock). T3 itself failed, so it needs no compensation, and T4 never runs.

3. Design rules for a correct saga

  • Compensation is semantic undo, not rollback. A refund is not "un-charging": the customer sees a charge and a refund, and the payment provider may keep a fee. A sent email cannot be unsent, so the compensation is a correction email. Design each compensation as a real business action.
  • Compensations must be idempotent. They will be retried, possibly concurrently with a delayed duplicate of the original step. "Refund charge ch_123" must be safe to run twice (use the charge id or an idempotency key).
  • Compensations must be retried until they succeed. A compensation that fails permanently leaves money or stock in limbo. Retry with backoff forever, and page a human (or open a manual-intervention task) if it stays stuck. This is why compensations should be simple and have few dependencies.
  • Order the steps by how hard they are to undo. Think of three groups:
    1. Compensable transactions: can be undone (reserve stock, place a hold on funds, create a label).
    2. The pivot transaction: the point of no return. If it succeeds the saga is committed to finishing; if it fails the saga compensates. In the store, a defensible pivot is "the carrier takes the parcel". Some teams treat a successful card capture as the pivot instead; what matters is that you decide where it is.
    3. Retriable transactions: steps after the pivot that must eventually succeed and are safe to retry forever (send the confirmation, update analytics). They never trigger compensation.
    Put risky, failure-prone or expensive-to-undo steps late and cheap, easily reversed ones early.
  • Persist the saga's progress. Every saga has a unique saga / correlation id (the order id works) and a durable record of which steps are done, in flight or compensated. Without it, a crash loses the thread. This is the state a workflow engine keeps for you.
  • Use timeouts everywhere. A step that never replies must eventually count as failed (or be checked), otherwise the saga hangs forever.
  • Handle "unknown outcome". After a timeout you don't know whether the downstream work happened. Either query the downstream by your correlation id ("is there a charge for order 8123?") or simply retry with the same idempotency key so the downstream deduplicates. Never retry a non-idempotent call blind.

4. Two ways to coordinate: orchestration vs choreography

Someone has to decide "what runs next" and "what do we undo". There are two styles.

Orchestration. A central orchestrator (a state machine or workflow) holds the saga's logic. It sends a command to each service ("reserve stock"), waits for the reply, decides the next step, and on failure issues the compensation commands. Services don't know about each other; they only know how to execute their own command.

Pros

  • The whole flow is in one place: easy to read, test, monitor
  • Adding or reordering steps touches one component
  • No cyclic dependencies between services
  • Simple to answer "where is order X?"

Cons

  • Risk of a central coupling point and single point of failure (mitigate by running it on a durable engine)
  • Danger of a "god service" holding business logic that belongs elsewhere
  • One more component to build and operate (unless you buy it)

Choreography. No central brain. Each service does its local transaction and publishes an event to a broker (Kafka, SNS/SQS, RabbitMQ). The next service subscribes to that event and reacts. For compensation, a failing service publishes a failure event (PaymentFailed) and earlier services subscribe to it and undo their work (StockReleased).

Pros

  • No central coordinator to build or fail
  • Services stay loosely coupled; easy for a small saga of 2 or 3 steps
  • Natural fit when events already flow on a broker

Cons

  • The flow exists only implicitly across many services: hard to follow and document
  • Risk of cyclic event dependencies
  • Hard to debug and monitor as it grows; no single place for "status of order X"
  • Adding a step means editing several services
Rule of thumb

Choreography for sagas of about 2 to 3 steps among services that already communicate by events. Orchestration as soon as there are more steps, branching, timers, human steps or you need visibility. In interviews, orchestration backed by a durable engine is usually the stronger default answer.

5. The lack of isolation

Sagas give you ACD, not ACID: atomicity (eventually, via compensation), consistency and durability, but no isolation. Because each local transaction commits immediately, other transactions can see the saga's intermediate state, and that state may later be compensated away. Typical anomalies:

  • Dirty reads: someone reads "stock reserved" or "payment charged" for an order that is later cancelled.
  • Lost updates: a second saga overwrites a change the first saga made, which the first saga's compensation then clobbers.
  • Non-repeatable reads: two reads inside one saga return different values because another saga changed the data in between.

Countermeasures (from the "Microservices Patterns" literature):

  • Semantic lock: a flag or status such as PENDING or reserved_by = order_8123 marks a record as being part of an unfinished saga. Other transactions skip it, wait, or treat it as unavailable. The saga clears it at the end (or in compensation).
  • Commutative updates: design operations so order doesn't matter (stock = stock - 1 / stock = stock + 1 rather than stock = 41), so interleavings and compensations compose safely.
  • Pessimistic view: reorder the steps so the dangerous anomaly can't happen. For example, take the reversible "hold" first and make the irreversible decrement last.
  • Reread value: before overwriting, re-read the record and check it is unchanged (an optimistic check). Use a version column or compare-and-set so a stale write fails instead of silently winning. See Dealing with Contention for optimistic concurrency control.
  • By value: pick the mechanism by business risk. Low-value orders can use the cheap countermeasures above; high-risk ones (large transfers) can be routed through stronger mechanisms such as a distributed lock or a single partition.
  • Design the UI and states honestly: show "Order pending" or "Payment processing", never "Confirmed" until the saga reaches its terminal state. Intermediate states are part of the product.

6. Reliability plumbing: outbox and inbox

Each saga step has a dual-write problem: it must update its database and send a message (event or command). If it commits and then crashes before publishing, the saga stalls silently. If it publishes first and the commit fails, downstream acts on something that never happened.

The fix is the transactional outbox:

  1. In one local transaction, write the business change and a row into an outbox table describing the message to send. Either both commit or neither does.
  2. A separate relay reads new outbox rows and publishes them to the broker, then marks them sent. The relay can poll the table, or use change-data-capture (for example Debezium tailing the database log).
  3. Delivery is at least once: the relay may publish, crash before marking, and publish again. So duplicates are normal.

The receiving side therefore needs an idempotent consumer (sometimes called an inbox): record the ids of processed messages in the same local transaction as the work, and ignore any message id it has already seen. Outbox + inbox together approximate exactly-once effects on top of at-least-once delivery.

BEGIN;
  UPDATE inventory SET reserved = reserved + 1 WHERE sku = 'A1' AND ...;
  INSERT INTO outbox (id, saga_id, type, payload)
    VALUES (gen_random_uuid(), 'order-8123', 'StockReserved', '{...}');
COMMIT;
-- relay: SELECT ... FROM outbox WHERE sent_at IS NULL; publish; UPDATE ... SET sent_at = now();

7. Relationship to workflow engines

An orchestrated saga needs: a durable record of progress, retries with backoff, timers, timeouts, a way to wait for external events, and a log of what happened. That is precisely what Temporal and AWS Step Functions provide. They are, in effect, a saga orchestrator you don't have to build. The canonical way to write a saga in Temporal is to append a compensation to a list each time a step succeeds, and on failure run that list in reverse (full code in Step 3 below).

If asked: "Why a saga instead of two-phase commit?"
"2PC would need every service and the payment provider to support distributed transactions, it holds locks across all of them while a coordinator decides, and if the coordinator dies the participants are stuck in doubt. That kills availability, and it can't span a warehouse worker who takes two days. So I use a saga: each service commits a local transaction and I define a compensating action for each, like refund or release stock, run in reverse if a later step fails. I give up isolation, so I add semantic locks like a PENDING status, make every step and compensation idempotent, and use an outbox so state and events can't diverge. I'd run it as an orchestrated workflow so the state, retries and timers are durable."

Step 3Durable workflow engines (Temporal, Step Functions and friends)

Once a workflow spans days and has to survive failures and retries, stop building the plumbing. A workflow engine (also called durable execution) lets you write the process as ordinary code or a declarative state machine. The engine records every step it completes, and when a machine dies the workflow picks up exactly where it left off, with retries and a full history of what happened.

How durable execution works

  • Event-sourced history. The engine stores an append-only log per workflow execution: "workflow started", "activity reserve_inventory scheduled", "activity completed with result X", "timer started", "signal received", and so on. This log is the workflow's state.
  • Workflow code vs activities. The workflow function contains only orchestration logic. Anything with a side effect (HTTP call, database write, sending an email) lives in an activity. Activities may fail and are retried; their results are recorded in the history.
  • Replay on recovery. When a worker crashes (or the workflow is evicted from memory after a long sleep), another worker loads the history and re-executes the workflow function from the top. Each time the code reaches an activity call that already has a recorded result, the engine returns that result immediately without running it again. When the code reaches the first call with no result, it continues for real. The workflow appears to resume mid-function, even though no thread was ever kept alive.
  • Determinism is mandatory. Because the code is replayed, it must make the same decisions given the same history. So workflow code must not call random(), read the wall clock, spawn raw threads, or do I/O directly. Use the engine's APIs instead (workflow.now(), workflow.sleep(), side-effect and random helpers). Violations surface as "non-determinism errors" on replay.
  • Timers cost nothing. await sleep(3 days) just records a timer in the history. No process is blocked, nothing polls, and it survives restarts. This is how "cancel if not picked within 3 days" and "send a reminder tomorrow" become one line of code.
  • Signals for human-in-the-loop events. An external system (the warehouse app) sends a signal such as item_picked to the running workflow by id. The workflow waits for it, optionally with a timeout. AWS Step Functions does the same with the callback pattern (.waitForTaskToken): the state pauses until someone calls SendTaskSuccess with the token.
  • Queries for status. A read-only query ("what step is order 8123 on?") inspects workflow state without changing it. This replaces the scattered status columns and powers a status page. (Pushing it to the browser: Real-Time Updates.)
  • Child workflows split a big process into sub-workflows (one per shipment, say) with their own histories and failure handling.
  • Versioning. Workflows can be running for weeks, so changing the code can break replay of in-flight executions. Engines provide versioning/patching APIs (Temporal's patched()/worker versioning) or you start new executions on new code and let old ones drain.
  • History limits. Histories are bounded (on the order of tens of thousands of events in Temporal and Step Functions). Long-lived loops use "continue-as-new" or restart themselves with fresh history.

Activities: retries, timeouts and idempotency

The engine retries failed activities according to a retry policy (initial interval, backoff coefficient, maximum interval, maximum attempts, and a list of non-retryable errors such as "card declined"). Timeouts bound each phase of an activity. In Temporal terms:

TimeoutWhat it boundsWhy you set it
Schedule-to-startTime an activity task waits in the queue for a workerDetects that no worker is available or workers are overloaded
Start-to-closeOne execution attempt of the activityThe key one: a hung API call is cut off and retried
Schedule-to-closeTotal time including all retriesCaps how long a step may keep trying overall
HeartbeatGap between "I'm alive" signals from a long activityDetects a crashed worker quickly during long-running work, and lets it resume from a checkpoint

Engines give you at-least-once activity execution: an activity may run, succeed, and have its completion lost to a crash, so it runs again. Hence activities must be idempotent. The standard technique is an idempotency key: a stable unique id (order id plus step name) sent with the call. The downstream service stores the key with the result and, on a repeat, returns the original result instead of redoing the work. Stripe accepts an Idempotency-Key header for exactly this. That is how you achieve "charge the card exactly once, effectively" on top of at-least-once delivery. For unknown outcomes (timeout), retry with the same key.

The store order as a Temporal-style saga

Pseudo-code in Python in the style of the Temporal SDK. Notice how the saga, the waiting for a human, the timeout, and the compensation are all just normal control flow:

@workflow.defn
class OrderWorkflow:
    def __init__(self):
        self.picked = False

    @workflow.signal                      # sent by the warehouse app
    def item_picked(self):
        self.picked = True

    @workflow.query                       # powers "where is my order?"
    def status(self) -> str:
        return self._status

    @workflow.run
    async def run(self, order: Order) -> str:
        compensations = []                # undo actions, newest last
        opts = dict(start_to_close_timeout=timedelta(seconds=30),
                    retry_policy=RetryPolicy(maximum_attempts=5,
                        non_retryable_error_types=["CardDeclined"]))
        try:
            self._status = "RESERVING"
            await workflow.execute_activity(reserve_inventory, order, **opts)
            compensations.append((release_inventory, order))

            self._status = "CHARGING"      # idempotency key = order.id
            await workflow.execute_activity(charge_card, order, **opts)
            compensations.append((refund_card, order))

            self._status = "LABELING"
            await workflow.execute_activity(create_label, order, **opts)
            compensations.append((void_label, order))

            self._status = "AWAITING_PICK"  # human step, can take days
            await workflow.wait_condition(lambda: self.picked,
                                          timeout=timedelta(days=3))

            # pivot passed: from here on we only move forward
            await workflow.execute_activity(
                send_confirmation, order,
                start_to_close_timeout=timedelta(seconds=30),
                retry_policy=RetryPolicy(maximum_attempts=0))  # retry forever
            return "COMPLETED"

        except (ActivityError, asyncio.TimeoutError):
            self._status = "COMPENSATING"
            for activity, arg in reversed(compensations):
                await workflow.execute_activity(
                    activity, arg,
                    start_to_close_timeout=timedelta(seconds=60),
                    retry_policy=RetryPolicy(maximum_attempts=0))  # until it works
            return "CANCELLED"
  • compensations is the saga's undo log: a step is added only after it succeeds, and on failure the list is run in reverse.
  • Compensation activities are retried without a cap, because a compensation must not fail permanently. Alert on them when they exceed a threshold.
  • If the process running this function dies at any line, replay brings another worker back to that exact line with all local variables (including compensations) reconstructed from history.
  • Real code also handles cancellation (run compensations in a detached/shielded scope so a cancel request doesn't abort the cleanup) and puts the pivot decision explicitly in the code.

In AWS Step Functions the same flow is a JSON state machine in the Amazon States Language (Task, Choice, Wait, Parallel, Catch and Retry blocks), drawn and debugged in a visual designer. A Catch on the failing state routes to compensation states. It is excellent for flows that mostly call AWS services; the trade-off is that complex logic becomes verbose JSON.

Trade-offs & pitfalls

This is where interviews are won. Each mechanism has a characteristic failure, and you should be ready to name it and its fix.

No isolation, so users see intermediate states

A customer may briefly see an order as "paid" that is later cancelled, or another buyer may see stock as unavailable while a reservation is pending. Use explicit pending states, semantic locks, and UIs that don't promise more than the saga has delivered. Often it is enough to make the intermediate state obviously provisional.

Compensation that cannot fully undo

Refunds take days and may cost fees; emails and physical shipments can't be recalled. Order steps so irreversible actions come last, and make compensation a business process (correction email, return label, credit) rather than assuming a perfect undo. Some failures end in a manual intervention queue, and your design should say so.

Duplicates and idempotency gaps

At-least-once delivery from brokers, retries from engines and users double-clicking all produce duplicates. Every step, every compensation and every consumer needs an idempotency key or a dedupe record. The engine retries safely only if the activity is idempotent.

Stuck sagas

A saga can sit forever waiting for a reply or a human. Give every wait a timeout and an escalation path (retry, alert, cancel). Monitor "sagas older than N" and sagas in COMPENSATING state, and keep a dead-letter or manual queue for ones that cannot proceed.

Orchestrator as a bottleneck or single point of failure

A hand-built orchestrator that holds state in memory is a liability. Persist saga state, run multiple instances, or use a durable engine whose availability and scaling are handled for you. Also keep business logic in the services; the orchestrator should only decide what happens next.

Workflow versioning and long-running deploys

A workflow started last week was written against last week's code. Changing step order or adding a step can break replay for in-flight executions. Plan for versioned workflows, or run old and new code side by side until old executions finish.

Volume and cost

Durable engines persist every step. At very high throughput (millions of tiny workflows) cost, history size and write amplification matter. Batch small items into one workflow, or keep the engine for the coordination-heavy flows and use a simple queue for the rest.

When NOT to use it

  • A 2-step flow inside one database. If both writes live in the same database, use a plain transaction. A saga is for work that spans transaction boundaries, not a replacement for them.
  • Simple fire-and-forget jobs. Resizing an image or sending one email needs a queue and a worker, not a workflow engine. See Managing Long-Running Tasks.
  • Short flows owned by one service. A hand-rolled, well-tested state machine with a status column is fine and cheaper to run.
  • Data pipelines and batch ETL. Use a batch orchestrator such as Airflow; this pattern is about request-driven business processes.
  • Steps that must be strictly isolated. If intermediate state must never be visible (a rare bank-internal ledger operation), keep the data in one database or one partition and use a real transaction instead of a saga.
  • Premature infrastructure. If you can't state what a failure in the middle would cost, you probably don't need an engine yet. Say so, and name the signal (steps, duration, humans, compensation) that would change your mind.

Interview script

Say it like this
"Checkout spans inventory, payments, shipping and a human in the warehouse, and it can take days, so I can't use one database transaction. I'll model it as an orchestrated saga: reserve inventory, charge the card, create the label, wait for the warehouse pick, then send the confirmation. Each step is a local transaction with a compensation, such as release stock, refund or void the label, run in reverse if something fails. The steps and compensations are idempotent using the order id as the idempotency key, and I'd use a transactional outbox for any events. Rather than hand-rolling status columns and cron jobs, I'd run this on Temporal or Step Functions, which persists each step, retries failures, sleeps for days for free, and takes the warehouse event as a signal. The risks I'd call out are lack of isolation, so I show a pending state and use semantic locks, and compensations that can't fully undo, which I'd handle with a manual queue."

Deep-dive Q&A

Why use a saga rather than two-phase commit, and what do you give up?

2PC holds locks across all participants while a coordinator decides, blocks if the coordinator fails, needs every system to support XA (third-party APIs and most NoSQL stores don't), and cannot span multi-day human steps. A saga commits local transactions independently and uses compensations to reverse on failure, which keeps services autonomous and available. You give up isolation: other transactions can observe intermediate state, so you add semantic locks, pending states, commutative updates and version checks, and you must write and operate compensations.

How do you guarantee the card is charged exactly once?

You can't get true exactly-once delivery, but you get exactly-once effect. Generate a stable idempotency key (order id plus step) and send it with the charge request. The payment provider stores key and result, and returns the original result for repeats. The workflow engine then may retry the activity as often as it likes. For a timeout with unknown outcome, retry with the same key or query the provider by that key before deciding. Add a unique constraint on your own side (for example one successful charge per order) as a second guard.

The worker running the workflow crashes in the middle. What happens?

Nothing is lost, because state lives in the engine's event history rather than in the worker. The engine notices the task timed out and hands it to another worker. That worker replays the workflow function against the recorded history: activities that already completed return their stored results immediately, so they are not re-run, and execution continues from the first step without a result. An activity that was in flight when the crash happened is retried, which is why it must be idempotent.

Why does workflow code have to be deterministic?

Recovery works by re-running the code and matching each call to the recorded history. If the code takes a different branch on replay (because of a random number, the current time, an unordered map iteration or a changed code path), the engine can no longer line the code up with the history and raises a non-determinism error. So all non-deterministic or side-effecting work goes into activities, and time, randomness and sleeping go through the engine's APIs. Changing workflow code for in-flight executions needs explicit versioning for the same reason.

What if a compensation itself fails?

Compensations must not be allowed to fail permanently. Make them idempotent and simple, retry them with backoff indefinitely, and alert if they exceed a threshold. If a compensation is blocked by something a retry can't fix (account closed, provider contract issue), the saga moves to a manual-intervention state with all context in its history so a human can resolve it. Never silently drop a failed compensation. Designing steps so the expensive, risky operations come late reduces how many compensations are ever needed.

Orchestration or choreography for this checkout, and why?

Orchestration. The flow has four or more steps, a human wait, timers and compensation, and the business needs a single answer to "where is order X?". An orchestrator (backed by a durable engine) keeps the flow in one readable place and avoids cyclic event dependencies. Choreography is reasonable for a tiny saga of two or three steps between services that already publish events, but it gets hard to follow and debug as steps are added. Even in an orchestrated design, services can still publish domain events for other consumers such as analytics.
