Scaling Reads

Your database can only answer so many queries per second. When reads outgrow it, you climb a ladder of fixes, from cheap and local (indexes) to heavy and distributed (caches and CDNs), and you pay a consistency price at each rung.

Read-heavy apps Caching Replication Eventual consistency

TL;DR

Most consumer apps are read-heavy. Ratios of 10:1 to 100:1 reads to writes are common, so reads are usually the first thing to fall over. Scale them in this order, and stop as soon as the problem is solved:

  1. Get more out of the database you already have: indexes, denormalization, materialized views.
  2. Add read replicas: copies of the database that serve reads while the primary handles writes.
  3. Add a cache (Redis, Memcached) in front of the database.
  4. Add a CDN for anything static or public.

Every rung makes reads faster and cheaper, but also makes data staler. Replicas lag, caches go stale, and a single hot key can melt a cache node. Being able to name these trade-offs and the fix for each is what the interviewer is looking for.

Recognize it when…
  • The prompt describes a feed, a catalogue, a profile page or a search results page.
  • Someone says "millions of users, mostly browsing."
  • The read-to-write ratio is stated or obviously lopsided (viewing vs posting, watching vs uploading).
  • A single page load fans out into many queries (post, author, like count, comments…).

The problem

Picture Instagram. You open the app and see a dozen or more photos. Each one needs its own metadata: the poster's profile, the like count, a few comments. Naively, that is several queries per photo, so one scroll can turn into hundreds of database queries. Meanwhile, you personally post about once a day.

Multiply by millions of users and the database spends nearly all its time answering reads. CPU saturates, connection pools run dry, query latency climbs and the whole app slows down, including the rare writes.

Do the math out loud

Interviewers like back-of-envelope numbers. For example: 100M daily users × ~10 feed loads/day × ~20 items each = 20B item reads/day, which is about 230K reads/second on average and several times that at peak. One well-tuned relational database is nowhere near that, so you must design for it.

When it comes up

It appears in almost every consumer-facing design. Typical prompts:

  • Instagram / Twitter / Facebook news feed: reading dwarfs posting.
  • YouTube / Netflix catalogue and watch pages: metadata is read constantly, rarely changed.
  • Amazon / e-commerce product pages: huge browsing volume versus orders.
  • URL shortener: write once, redirect millions of times.
  • Wikipedia, news sites, blogs: public content that changes rarely.

Solutions, in escalation order

Always start with the cheapest fix that could work. Each step below adds operational complexity and a new way to serve stale data, so don't skip ahead.

Step 0Get the most out of your existing database

Before adding any infrastructure, make sure the database is not doing needless work.

Indexes

An index (usually a B-tree) lets the database jump straight to matching rows instead of scanning the whole table, turning an O(n) scan into roughly O(log n). For the feed query "latest 20 posts by this user":

CREATE INDEX idx_posts_user_created
  ON posts (user_id, created_at DESC);

SELECT id, caption, created_at
FROM posts
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
  • Composite indexes follow the leftmost-prefix rule: an index on (user_id, created_at) serves queries filtering on user_id, or on both, but not on created_at alone. Column order matters.
  • Covering indexes include every column the query needs, so the database can answer from the index alone (an "index-only scan") without touching the table.
  • Trade-off: every index must be updated on every write and takes disk and memory. Index what you query, not everything.
  • Use EXPLAIN ANALYZE to confirm the planner actually uses your index.

Denormalization

Normalized schemas need joins, and joins are expensive at scale. Denormalizing means deliberately storing redundant data so a read touches one row instead of many:

  • Keep like_count and comment_count on the post row instead of running COUNT(*) over a likes table on every view.
  • Copy the author's name and avatar URL into the post (or into a feed table) so rendering a post needs no join to users.
  • Trade-off: writes get more complex because you must update every copy, and copies can drift apart. Good for data that is read often and changes rarely.

Materialized views and precomputed tables

A materialized view stores the result of an expensive query (a leaderboard, a "trending" list, per-user stats) as a real table that you refresh on a schedule or trigger. In PostgreSQL: REFRESH MATERIALIZED VIEW CONCURRENTLY trending_posts;. The same idea underlies feed tables that are precomputed per user ("fan-out on write").

Step 1Read replicas

When one machine still cannot keep up, copy the database. A read replica is a follower that receives a stream of every change from the primary (the write-ahead log in PostgreSQL, the binlog in MySQL) and applies it. Your application sends writes to the primary and spreads reads across the replicas. Read capacity then grows roughly linearly with replica count. Amazon Aurora, for example, supports up to 15 replicas per cluster.

Pros

  • Simple, no application data-model changes
  • Linear read scaling
  • Doubles as high availability: a replica can be promoted if the primary dies
  • Can dedicate a replica to heavy analytics queries

Cons

  • Replication lag: replicas are slightly behind
  • Does nothing for write throughput, since every replica applies every write
  • Need read/write routing logic or a proxy
  • Each replica holds the full dataset (storage cost)

Sync vs async replication

  • Asynchronous (the default for read scaling): the primary acknowledges the write immediately and ships it to replicas afterward. Fast, but replicas may be behind by milliseconds to seconds, and unreplicated writes can be lost if the primary crashes.
  • Synchronous: the primary waits for at least one replica to confirm. No lost data and no lag on that replica, but writes are slower and a stuck replica can stall them. Often used as semi-synchronous: wait for one replica, not all.

Fixing "I posted, but I can't see my post"

This is the canonical replica-lag bug, called a read-your-writes violation. Common fixes, from simplest to most precise:

  1. Route the author's own reads to the primary for a short window (say 5–10 seconds) after they write, or for the specific object they just changed.
  2. Sticky sessions / session pinning to the primary after a write.
  3. Version tokens: on write, return the log position (PostgreSQL LSN, MySQL GTID) to the client; on read, only use a replica that has replayed at least that position, otherwise fall back to the primary.
  4. Optimistic UI: the client shows the new post locally right away, so the lag is invisible.
  5. Accept it for data where staleness is harmless (other people's like counts). Not everything needs strong consistency.

Step 2Add a cache

If the same data is read again and again, serve it from memory instead of re-querying. An in-memory key-value store such as Redis or Memcached returns results in well under a millisecond and takes enormous load off the database. A relatively small hot set of data usually serves the vast majority of reads, so even a modest cache achieves a high hit rate.

Caching strategies

StrategyHow it worksGood for / watch out
Cache-asideApp checks cache; on a miss it reads the DB and fills the cache.Default choice. Only requested data is cached. First request is slow; cache can serve stale data.
Read-throughSame idea, but the cache layer itself loads from the DB on a miss.Simpler app code. Needs a cache that supports loaders.
Write-throughWrites go to the cache and the DB synchronously.Cache is always fresh for written keys. Writes are slower; caches data that may never be read.
Write-behind (write-back)Writes hit the cache, which flushes to the DB asynchronously.Very fast writes. Risk of data loss if the cache dies before flushing.
Write-aroundWrites go straight to the DB, bypassing the cache.Avoids filling the cache with rarely-read data. First read after a write is a miss.

Keeping the cache correct (invalidation)

The cache is a copy, so it can disagree with the database. Your plan for that disagreement is the real design question:

  • TTL (time to live): every entry expires after N seconds, which bounds how stale it can be. Simple and robust; choose TTL by how wrong the data is allowed to be (seconds for like counts, hours for profile photos).
  • Explicit invalidation: on write, delete the key (prefer delete over update, which avoids some race conditions) so the next read refills it.
  • Event-driven invalidation: publish change events (for example via change-data-capture such as Debezium reading the database log) and have a consumer evict the affected keys.
  • Versioned keys: include a version in the key (post:123:v7), so new versions never collide with old ones.
  • Eviction policy (LRU, LFU) decides what gets thrown out when memory is full. It is separate from invalidation.
  • Negative caching: briefly cache "not found" results too, so a flood of requests for a non-existent key cannot hammer the database ("cache penetration").
A subtle race in cache-aside

Reader A misses and reads the old value from the DB. Writer B updates the DB and deletes the cache key. Reader A then writes its stale value into the cache. The cache now holds old data until the TTL runs out. This is why a TTL is almost always kept as a safety net, even when you also invalidate explicitly.

Step 3Add a CDN

A content delivery network caches copies of content on servers close to users around the world (edge locations / points of presence). It is the right tool for anything static or shared between users: images, video segments, JavaScript and CSS bundles, public pages, and anonymous GET API responses. Users get lower latency, and your origin servers and databases never see most of the requests.

  • Control behavior with HTTP headers: Cache-Control: public, max-age=3600, s-maxage for shared caches only, stale-while-revalidate to serve old content while refreshing in the background.
  • For assets that never change, use content-hashed file names (app.3f9c2a.js) with a very long max-age plus immutable. "Invalidation" becomes just deploying a new file name.
  • Explicit purges are possible (CloudFront invalidations, Cloudflare purge API) but are slow, rate-limited or costly at scale, so design around TTLs and versioned URLs where you can.
  • Not suitable for personalized or private data unless you carefully vary on the right keys or use signed URLs/cookies.

Trade-offs & pitfalls

This is where interviews are won. Each technique has a characteristic failure, and you should be ready to name it and its fix.

Replica lag

Covered above: users can fail to see their own writes. Mitigate with primary-routing windows, version tokens, or optimistic UI, and monitor replica lag so you can pull a lagging replica out of rotation.

Stale caches

Decide how much staleness each kind of data tolerates and pick TTLs to match. Combine TTL with explicit delete-on-write for data that must update quickly.

Hot keys

When millions of people request the same celebrity's post at once, one cache key on one cache node receives all of that traffic. Adding more cache nodes doesn't help, because the key still lives on exactly one of them and that node's CPU or network saturates. Options:

  • Local in-process cache with a very short TTL (1–5 seconds) on every app server. Most requests never leave the machine, and a few seconds of staleness is usually fine.
  • Replicate the key under N names (post:123#0 … post:123#7), spread across nodes, and have readers pick one at random.
  • Serve it from the CDN if the content is public.
  • Request coalescing ("single-flight"): when many requests need the same missing value, let one fetch it while the others wait for its result.
  • Detect it: monitor per-key traffic (Redis can report hot keys when LFU eviction is enabled) so you can react before a node falls over.

Cache stampede (thundering herd)

A very popular key expires, and thousands of concurrent requests all miss at once and rush to the database to rebuild it. The database can be overwhelmed by exactly the traffic the cache was supposed to absorb. Fixes:

  • Lock or single-flight on rebuild: only one request recomputes; the rest wait or serve the old value.
  • Stale-while-revalidate: keep serving the expired value while one background refresh runs.
  • TTL jitter: add a random amount to each TTL so many keys don't expire together.
  • Probabilistic early refresh: each reader has a small, growing chance to refresh the key shortly before it expires.
  • Pre-warm the cache for known-hot data, especially after a deploy or cache restart.

The cache is not your source of truth

A cache node can die or be flushed. Your system must still work, just more slowly, with the database absorbing the load. Protect it with rate limiting, circuit breakers and gradual cache warm-up so a cold cache doesn't cause a cascading outage.

When NOT to use it

  • Don't cache before indexing. A missing index is the most common cause of a "slow database", and a cache just hides it. Check EXPLAIN first.
  • Modest traffic. A single well-indexed relational database handles a lot of read traffic. If your numbers don't demand more, don't add replicas and caches "just in case".
  • Data that must be strongly consistent (account balances, remaining inventory, seat availability at checkout) should be read from the primary, not from a cache or lagging replica.
  • Low-reuse or highly personalized data. If each item is read once, a cache has nothing to hit.
  • The real bottleneck is writes. Replicas and caches won't help. See Scaling Writes.

Interview script

Say it like this
"This is read-heavy, probably 100 to 1 reads to writes, so reads are what will break first. I'll start by making sure the queries are indexed and denormalize the like and comment counts to avoid joins. If one database still can't handle it, I'll add read replicas and route the author's own reads to the primary so they always see their own posts. In front of that I'll put Redis with cache-aside and short TTLs, and a CDN for media. The risks I'd watch are replica lag, stale cache entries, and hot keys for celebrity content, which I'd handle with a short-lived in-process cache."

Deep-dive Q&A

A user posts, refreshes, and the post is missing. Why, and how do you fix it?

The write went to the primary, but the refresh read from an asynchronous replica that hadn't received it yet. Fix it by routing that user's reads to the primary for a short window after a write (or by passing a log-position token and only using replicas that have caught up). Optimistic UI hides the lag on the client.

How do you invalidate a cache?

Use layers. A TTL guarantees a bound on staleness, delete-on-write keeps hot data fresh, and change-data-capture events can evict keys when data changes through other paths (batch jobs, other services). Choose the TTL by how stale the business can tolerate. Keep the TTL even when you invalidate explicitly, because invalidation can fail or race.

Your Redis cluster restarts and the cache is empty. What happens?

Every request misses and goes to the database at once, a cold-start stampede that can take the database down. Mitigate with request coalescing, rate limiting or load shedding in front of the DB, gradual traffic ramp-up, pre-warming known-hot keys, and Redis replication or persistence so a single node failure doesn't wipe the cache.

Read replica or cache: which first?

Replicas are generic: they serve any query, including complex ones, with no application changes beyond routing, but scale reads only linearly with cost. Caches are far cheaper per read and faster, but only help for repeated, key-addressable reads, and add invalidation logic. Most systems end up with both. Start with whichever matches the access pattern: ad-hoc or varied queries lean toward replicas; repeated lookups of the same objects lean toward a cache.

How do you decide what to add next?

Measure. Look at query latency (p50/p99), database CPU and connection saturation, the slowest queries, cache hit ratio, and replica lag. Fix the largest bottleneck with the cheapest tool, then re-measure. In an interview, state the metric that would tell you each step is needed.
