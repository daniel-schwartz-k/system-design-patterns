Dealing with Contention

When many users try to change the same piece of data at the same instant, a naive read-check-write sequence lets two of them both win. Most of the time one database already has the tools to prevent that. The hard part comes when the data you must coordinate lives in more than one place.

Race conditions Locking Optimistic concurrency Double booking

TL;DR

Contention means many actors competing to modify the same data at the same moment. The classic failure is a race condition: two servers both read "one ticket left", both decide it is theirs, and both sell it. Ticketmaster's last seat and Airbnb booking one property for the same night are the same problem. So are bidding on an auction item, matching a driver to a rider, and decrementing a stock counter.

The key insight: a single relational database already solves most of this. Escalate in this order and stop as soon as the problem is solved:

  1. Atomic conditional write: make the check and the change one statement (UPDATE ... WHERE status = 'available') and look at how many rows changed. Add unique constraints as a lock-free guard.
  2. Pessimistic locking: lock the row while you work on it (SELECT ... FOR UPDATE). Others wait.
  3. Optimistic concurrency control (OCC): do not lock; write only if nobody changed the row since you read it (a version check), and retry if they did.
  4. Reservation with expiry for user-facing checkout flows: available to held (with expires_at) to sold.
  5. Only if the data truly spans several systems: distributed locks, two-phase commit, sagas, or serializing everything through a single queue per key.

The warning from experienced interviewers: candidates get into trouble at step 5. The moment you split data across databases you take on every coordination problem the single database was solving for you, and the interviewer will ask how you handle it. Do not split (shard) prematurely; keep contended data together in one database.

Recognize it when…
  • The prompt involves a scarce, limited resource: last seat, last item, a single room, a single driver, a single username.
  • Words like "booking", "reservation", "bidding", "inventory", "matching", "claim", "flash sale", "limited quantity", "exactly once".
  • Two requests could touch the same row at nearly the same time, and the business rule is "never oversell / never double-book / highest bid wins".
  • An invariant has to hold across concurrent users (balance never negative, one winner, count never exceeds capacity).
  • The interviewer asks "what if two users click at the same moment?"

The problem

Imagine a ticket table. The naive purchase code looks perfectly reasonable:

-- Alice's server and Bob's server both run this
ticket = SELECT * FROM tickets WHERE id = 7;      -- (1) read
if ticket.status == 'available':                  -- (2) check
    UPDATE tickets SET status = 'sold',           -- (3) write
                       owner = :me
    WHERE id = 7;

The code is correct for one user at a time. With two users, the steps can interleave: both reads happen before either write. Each server sees "available", each passes the check, each writes. The second write silently overwrites the first, and one seat now has two buyers who both received a confirmation.

Why it happens

  • Check-then-act is not atomic. Between your read and your write, the world can change. The time window may be milliseconds, but at scale (or under a flash sale) you hit it constantly.
  • Default isolation levels allow it. Most databases default to read committed (PostgreSQL, Oracle, SQL Server) or repeatable read (MySQL InnoDB). Under read committed, each statement sees the latest committed data, but nothing stops another transaction from committing a change between your SELECT and your UPDATE. A transaction by itself does not make a read-then-write safe.
  • A lost update is the general form: two transactions read the same value, both compute a new value from it, and the last write wins, erasing the other's change. A counter that two clients both read as 10 and both set to 11 should have ended at 12.
  • Several app servers make it worse. You cannot fix it with an in-process lock or synchronized block, because Alice and Bob are on different machines. The coordination must happen somewhere they both share: the database.
Name the invariant

Start by stating the rule that must never break: "a seat is sold to at most one person", "an account balance never goes negative", "only the highest bid wins". Everything below is a way to enforce that invariant under concurrency, and picking the right tool depends on how it is shaped (single row, many rows, or many systems).

When it comes up

Any design with a scarce resource and concurrent actors. Typical prompts:

  • Ticketmaster / event booking: thousands of fans chase the same seats the moment sales open.
  • Airbnb / hotel / restaurant reservations: one property, one night, many guests.
  • Online auction / bidding: concurrent bids must resolve to one highest bid, in order.
  • E-commerce flash sales / inventory: 100 units, 10,000 buyers; never sell 101.
  • Ride-hailing and matching: one driver must not be assigned two riders.
  • Payments and wallets: balance checks and transfers, double-spend prevention.
  • Unique resources: usernames, coupon codes redeemed once, "first N users get a prize", seat assignment on a flight.
  • Collaborative editing and config updates: two people edit the same document or record.

Solutions, in escalation order

Start with the cheapest tool that enforces your invariant. The first three steps live entirely inside one database, which is where you want to stay for as long as possible.

Step 1Atomic conditional update

The simplest and most underrated fix: collapse the check and the write into one SQL statement, so the database evaluates the condition and applies the change as a single atomic operation. The database takes a row lock internally for the duration of that statement, so two concurrent statements on the same row are serialized automatically.

UPDATE tickets
SET    status = 'sold', owner_id = :user
WHERE  id = 7
  AND  status = 'available';
-- then check the rows-affected count from your driver:
--   1  -> you got it
--   0  -> someone else already did (or it never existed)

Walk through the race: Alice's and Bob's statements arrive together. The database lets one proceed first; it flips the row to sold and commits. The other statement then re-evaluates its WHERE clause against the committed row (PostgreSQL does this re-check under read committed), finds status = 'sold', matches nothing and reports 0 rows. Exactly one buyer wins, with no explicit locking code and no retry loop.

Other single-statement guards

  • Atomic increments and decrements with a floor: UPDATE inventory SET qty = qty - 1 WHERE sku = 'X' AND qty > 0;. Never read the quantity into the app, subtract and write it back; that is the lost-update bug. Let the database do the arithmetic.
  • Unique constraints: let the schema enforce "at most one". A UNIQUE (event_id, seat_id) index on a bookings table means a second INSERT for the same seat fails with a unique-violation error. No locks, and the guarantee holds no matter how many app servers or code paths write to the table.
  • INSERT ... ON CONFLICT (PostgreSQL; INSERT ... ON DUPLICATE KEY in MySQL): claim-or-skip in one step, e.g. INSERT INTO claims (coupon, user_id) VALUES (:c, :u) ON CONFLICT (coupon) DO NOTHING; then check rows affected. This is also the standard way to build idempotent writes.
  • CHECK constraints (CHECK (qty >= 0)) act as a backstop: even a buggy code path cannot drive the value negative.

Pros

  • Simplest possible code; no transaction juggling
  • No waiting on locks held across network calls
  • Constraints enforce the rule for every writer, forever
  • Very fast: one round-trip

Cons

  • Only works when the rule fits in one statement
  • Cannot span multiple rows or tables with arbitrary logic
  • You must remember to check rows-affected (ignoring it reintroduces the bug)
  • Does not help if the work between read and write involves other systems

Step 2Pessimistic locking

If the logic between reading and writing is more than one statement (say, read the seat, read the user's credit, compute a price, then write), take a lock so nobody else can change the rows you are looking at until you finish. "Pessimistic" because it assumes a conflict will happen and prevents it up front.

BEGIN;
SELECT * FROM tickets WHERE id = 7 FOR UPDATE;   -- row is now locked
-- other transactions that try to lock or modify row 7 now WAIT here
-- ... validate, compute, call other tables ...
UPDATE tickets SET status = 'sold', owner_id = :user WHERE id = 7;
COMMIT;                                           -- lock released

With Alice holding the lock, Bob's SELECT ... FOR UPDATE blocks until Alice commits. When Bob finally gets the row, he reads the committed value (sold), sees it is gone, and rolls back cleanly. This is correct and easy to reason about.

Lock flavours worth knowing

  • FOR UPDATE: exclusive row lock; blocks other writers and other FOR UPDATE readers. Plain (non-locking) SELECTs are not blocked in MVCC databases like PostgreSQL and InnoDB.
  • FOR SHARE: shared lock; many readers can hold it, but no one can modify the row.
  • NOWAIT: fail immediately instead of waiting if the row is locked. Good for "try to grab it or tell the user it is busy".
  • SKIP LOCKED: silently skip rows other transactions have locked. This is the standard trick for work queues in a database: SELECT * FROM jobs WHERE status='pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED; lets many workers each claim a different job without blocking each other. Also useful to pick "any available seat" instead of a specific one.
  • Table and advisory locks: coarse table locks exist but are rarely what you want. PostgreSQL advisory locks (pg_advisory_xact_lock(key)) let you lock an arbitrary application-defined key, such as "user 42's checkout", even when no single row represents it.

The costs: duration, deadlocks, convoys

  • Lock duration. A lock is held from acquisition to commit. Keep transactions short: never call an external API, wait for a payment provider or wait for a human while holding row locks. Locks held across slow work make everyone else queue and can exhaust your connection pool.
  • Deadlocks. Transaction A locks seat 1 then wants seat 2; transaction B locks seat 2 then wants seat 1; each waits on the other forever. Databases detect this (a wait-for graph cycle check) and abort one victim with a deadlock error, so your code must be ready to retry. Prevent most of them with consistent lock ordering: always acquire locks in a fixed order (for example, sorted by seat id) across all code paths.
  • Lock convoys and queueing. A hot row means a growing line of waiters; throughput for that row is capped at one transaction at a time, and latency for the waiters grows with the line. Use lock timeouts (lock_timeout, innodb_lock_wait_timeout) so a stuck holder cannot stall everything.
  • Scope. Locking too many rows (or a range, via gap locks in InnoDB) reduces concurrency for unrelated users. Lock the narrowest thing that protects the invariant.

Pros

  • Strong guarantee; easy to reason about
  • Handles complex multi-statement logic and multi-row updates
  • No retry logic needed for ordinary conflicts (waiting resolves them)
  • Good when conflicts are frequent: waiting beats thrashing

Cons

  • Everyone on the hot row waits; throughput per row is serial
  • Deadlock risk; need lock ordering and retry on deadlock
  • Locks tie up connections; unsafe across user think-time
  • Only works inside one database; does not span services
Which of the two first?

If one conditional UPDATE can express your rule, use it (Step 1): it is shorter and holds locks for the shortest possible time. Reach for FOR UPDATE when you genuinely need to read, think, and then write several rows under one consistent view.

Step 3Optimistic concurrency control: why and how

Why it exists

Pessimistic locking is safe but expensive, and the expense is paid on every request, whether or not anyone is actually competing:

  • Everyone waits. Even when two users touch the same row only once in a thousand requests, every request pays the cost of acquiring and releasing a lock.
  • Locks span round-trips and think-time. In a web app the read and the write are often separate HTTP requests. A user may open a booking form, stare at it for five minutes, then press Submit. A lock held for that whole time blocks everyone else, and a user who closes the tab never releases it. Stateless HTTP servers and a pooled database connection make "hold a transaction open across requests" a non-starter.
  • Deadlocks and lock convoys become possible, and lock waits reduce throughput and tie up connections.
  • Often unnecessary. In many workloads (editing your own profile, updating a record that only a few people touch, booking from a large pool of mostly free seats) conflicts are rare. Paying for a lock every time to prevent something that almost never happens is wasteful.

Optimistic concurrency control (OCC) flips the assumption: assume there will be no conflict, do the work with no locks, and detect a conflict only at write time. If someone else changed the data in the meantime, your write is rejected and you start over (or tell the user). It is the same idea as compare-and-swap (CAS) in CPUs and lock-free data structures, applied to database rows.

When OCC wins

  • Low contention: conflicts are rare, so retries are rare
  • Read-heavy workloads: readers never block or are blocked
  • Long think times between read and write (forms, editors)
  • Distributed or stateless clients and HTTP APIs: nothing is held between requests
  • No deadlocks, no lock timeouts, no abandoned locks

When OCC loses

  • High contention / hot rows: most attempts fail and must be redone
  • Retry storms and livelock: many clients keep colliding and redoing the same work, burning CPU
  • Starvation: an unlucky client can lose repeatedly while others win
  • Expensive work between read and write is wasted on every failed attempt

How it works, step by step

Add a version to the row. Every successful write increments it. The whole technique is three phases:

  1. Read. Fetch the row and remember its version (say, v7).
  2. Compute / validate. Do whatever business logic you need. No locks are held, so this can take as long as it wants (including user think-time).
  3. Write conditionally. Update only if the version is still what you read, and bump it in the same statement: 
    UPDATE tickets
SET    status = 'sold',
       owner_id = $2,
       version  = version + 1
WHERE  id = $1
  AND  version = $3;      -- the version I read earlier
-- rows affected = 1: success, nobody changed it since I read it
-- rows affected = 0: someone else wrote first -> conflict

On a conflict (0 rows) you either retry, which means re-reading the fresh row, re-running the validation and trying again, usually with exponential backoff plus random jitter and a maximum number of attempts, or you surface the conflict to the user (HTTP 409 Conflict) and let them decide, which is the right answer for "someone else edited this record while you were looking at it".

Worked example: Alice and Bob, the last ticket

Ticket 7 is status = 'available', version = 7.

  1. Alice reads ticket 7: available, v7. Bob reads ticket 7: available, v7. Both see it is free; neither holds a lock.
  2. Alice submits UPDATE ... SET status='sold', owner=Alice, version=8 WHERE id=7 AND version=7. The version is still 7, so the row changes. Rows affected = 1. Alice's purchase succeeds; the row is now sold, v8.
  3. Bob submits the same statement with owner Bob and WHERE ... version=7. The row is now at version 8, so no row matches. Rows affected = 0. Bob has detected a conflict.
  4. Bob re-reads the ticket: sold, v8. His validation ("is it available?") now fails.
  5. Bob fails gracefully: the API returns 409 Conflict / "Sorry, that seat was just taken", and the UI offers other seats. There is no double booking, and no one waited on a lock.

The retry loop

import random, time

MAX_ATTEMPTS = 5

def buy_ticket(ticket_id, user_id):
    for attempt in range(MAX_ATTEMPTS):
        # 1. read (remember the version)
        row = db.fetch_one(
            "SELECT status, version FROM tickets WHERE id = %s", ticket_id)

        # 2. validate / compute (no locks held)
        if row.status != "available":
            raise SoldOut()                 # a business answer, not a retry

        # 3. conditional write: compare-and-swap on version
        n = db.execute(
            """UPDATE tickets
               SET status='sold', owner_id=%s, version = version + 1
               WHERE id=%s AND version=%s""",
            user_id, ticket_id, row.version)

        if n == 1:
            return "ok"                     # we won

        # n == 0: someone else changed the row; back off and redo everything
        time.sleep(random.uniform(0, 0.05 * 2 ** attempt))   # backoff + jitter

    raise Conflict()                        # surface as HTTP 409

Pitfalls

  • Retry the whole read-compute-write, not just the write. Re-sending the same UPDATE ... WHERE version = 7 will fail forever. After a conflict you must re-read, re-validate against the new state (it may no longer be valid) and recompute.
  • Side effects inside the retried section must be idempotent. If a retry attempt sends an email, charges a card or publishes an event before the conditional write, a retry repeats it. Do side effects only after the write succeeds, or use idempotency keys.
  • The ABA problem. If you compare values instead of versions, a row can change from A to B and back to A; your check passes even though the data changed in between, which may matter (for example, a balance went 100, then 40, then 100 after a refund). A monotonically increasing version never repeats, so any intervening write is detected.
  • The version bump must be in the same atomic statement as the data change. If you increment it in a separate statement, a gap appears in which another writer can slip through.
  • A per-row version does not protect multi-row invariants (write skew). Two doctors are on call; each checks "at least one other doctor is on call" and each removes themselves. They update different rows, so neither version check fires, yet the invariant breaks. Fix with a constraint, serializable isolation, or by locking/versioning a shared parent row (for example, the shift row).
  • Retry storms under hotspots. If hundreds of clients hammer one row, almost all attempts fail and every retry adds load. Use exponential backoff with jitter and an attempt cap, and when a specific path is persistently hot, switch that path to pessimistic locking, an atomic decrement, or queue serialization (Step 7).
  • Return a useful conflict. Expose 409/412 with a message so the UI can show "this was changed by someone else, reload".

If asked: why optimistic concurrency?
"Locks make every request pay for a conflict that rarely happens, and they can't be held across a user's think-time or an HTTP round-trip without hurting throughput and risking deadlocks. With optimistic concurrency I read the row and its version, do my work without locks, and write with a compare-and-swap on the version. If zero rows were updated, someone beat me, so I re-read and retry with backoff, or return a 409. It's ideal when contention is low. If one row turns out to be hot, I'd switch that path to an atomic update or serialize it through a queue instead of letting clients thrash."

Isolation levels: the database's built-in safety net

Instead of hand-writing locks and version checks, you can ask the database for stronger guarantees via the transaction isolation level. Know the ladder:

LevelWhat you seeDoes it stop the double sell?
Read committedEach statement sees the latest committed data. Default in PostgreSQL, Oracle, SQL Server.No: read-check-write still races, because the data can change between your statements.
Repeatable read / snapshotThe whole transaction sees one consistent snapshot. Default in MySQL InnoDB. In PostgreSQL, a write to a row that another transaction changed since your snapshot fails with a serialization error.Partly: detects lost updates on the same row (PostgreSQL), but still allows write skew. InnoDB's behavior differs and is not a pure snapshot for writes, so check your database.
SerializableThe result is as if transactions ran one at a time. PostgreSQL implements it as Serializable Snapshot Isolation (SSI): optimistic tracking, no extra blocking; MySQL and SQL Server use locking.Yes, including write skew, but any transaction may be aborted (SQLSTATE 40001) and must be retried.

Write skew example: two doctors are on call and the rule is "at least one must stay". Each transaction reads "2 on call", each removes itself, and both commit. They wrote different rows, so snapshot isolation sees no conflict, but the rule is broken. Only serializable isolation, a constraint, or explicitly locking a shared row catches it.

The pragmatic summary: serializable is the simplest to reason about (the database does optimistic control for you), at the price of more aborts and a mandatory retry loop. For a single hot invariant, a targeted conditional update or FOR UPDATE is usually cheaper and more predictable.

Reservation with expiry (hold pattern)

Checkout flows add a human to the loop: a fan picks a seat, then takes two minutes to enter card details. You cannot hold a database lock that long (see the OCC section), and you cannot just leave the seat "available" or someone else buys it while the first user is typing. The standard solution is a soft lock with a timeout, modelled as an explicit state:

-- 1. place a hold (atomic; only one request can win)
UPDATE tickets
SET    status = 'held', held_by = :user, expires_at = now() + interval '5 minutes'
WHERE  id = 7
  AND (status = 'available' OR (status = 'held' AND expires_at < now()));

-- 2. on successful payment (must still be MY unexpired hold)
UPDATE tickets
SET    status = 'sold', owner_id = :user
WHERE  id = 7 AND status = 'held' AND held_by = :user AND expires_at > now();
  • Expiry options: (a) a background job that periodically flips expired holds back to available; (b) make expiry implicit by including expires_at < now() in the availability condition, as above, so nothing needs to clean up for correctness; (c) store the hold in Redis with a TTL (SET hold:7 user NX EX 300) and treat the key's absence as "available". With Redis, the database only records the final sold, which must still be a conditional write, because the Redis hold alone is not a durable guarantee.
  • Choose the timeout carefully: long enough to pay, short enough that abandoned carts do not starve real buyers (Ticketmaster-style systems commonly hold for several minutes; treat any number you quote as an example).
  • Check at both ends: the payment step must verify the hold is still yours and unexpired; otherwise a slow payment could finalize a seat that was already re-sold.
  • Payment races: if the payment succeeds after the hold expired and the seat was resold, you need a refund path. Keep the hold a bit longer than the payment timeout to make this rare.
  • Everything here is still a single-database conditional write (Step 1), just with a richer state machine.
Don't split prematurely

Everything above works inside one database. A single well-provisioned PostgreSQL or MySQL instance handles thousands of such transactions per second, and contended data (seats for an event, inventory for a sku) is usually small. If you shard the data across databases, you lose cross-row transactions and row locks, and every operation that touches two shards now needs the distributed coordination below. Keep the contended data together; scale by sharding on a key (for example, event id) so that all rows that must be coordinated still live in one shard, and use read replicas and caches for the non-contended read traffic.

Step 4Beyond one database: distributed locks

Sometimes the thing you must protect is not a row in a single database: a resource shared by several services, a job that must run on exactly one worker, or data in a store with no transactions. A distributed lock is a lock whose state lives in a shared service that all participants can reach.

  • Redis: SET lock:seat:7 <random-token> NX PX 30000 (set only if absent, expire after 30 s). Release only if the stored token matches yours (a small Lua script does compare-and-delete atomically) so you never delete someone else's lock. The expiry is a lease: it makes sure a crashed holder cannot hold the lock forever.
  • ZooKeeper / etcd (Chubby-style): locks built on a consensus-backed store, using ephemeral nodes or leases tied to a session. Stronger guarantees than a single Redis node, at the cost of running a quorum.
  • Redlock is an algorithm that acquires the same lock on a majority of independent Redis nodes. It is controversial: critics (notably Martin Kleppmann) argue it depends on timing assumptions (bounded clock drift and pauses) that do not hold in real systems, so it is unsafe when correctness, not just efficiency, depends on the lock. Defenders disagree. The safe takeaway: use a Redis lock for efficiency (avoid duplicate work), and use a consensus system plus fencing when mutual exclusion is critical.

The core danger: lease expiry and pauses

The holder acquires a 30-second lease, then stalls (a long garbage-collection pause, a network partition, a busy VM) for longer than the lease. The lease expires, a second client acquires the lock, and then the first client wakes up, still believing it holds the lock, and writes. Now two writers act "exclusively" at once. A lock with a timeout alone cannot prevent this, because the holder cannot know it lost the lock.

Fencing tokens

The fix is to make the resource itself reject stale holders. The lock service hands out a monotonically increasing number with each grant (token 33, then 34, and so on). The client sends the token along with every write, and the storage layer remembers the highest token it has seen and rejects any write with a lower one. When the paused client wakes up and sends token 33 after 34 has been used, the write is refused. Notice this is again optimistic concurrency control: a version check at the data store. ZooKeeper (zxid / node version) and etcd (revision) provide such monotonic numbers; a plain Redis lock does not.

Pros

  • Works across services and datastores with no shared transaction
  • Good for "only one worker does this job" and leader election
  • Redis locks are quick to set up and low latency

Cons

  • New failure modes: expiry, pauses, partitions, clock drift
  • Needs fencing for real safety, and the data store must cooperate
  • Extra infrastructure on the critical path; the lock service becomes a bottleneck and a dependency
  • Easy to get subtly wrong; interviewers will probe it

Step 5Two-phase commit (2PC)

When one logical operation must update several databases atomically (all commit or none), 2PC provides it. A coordinator runs two phases: in the prepare phase it asks every participant "can you commit?", and each participant durably logs the change, takes its locks, and votes yes or no; in the commit phase, if everyone voted yes the coordinator tells all to commit, otherwise it tells all to abort. It gives atomicity across databases (the XA standard, and what Spanner and distributed SQL systems do internally).

Why it hurts: it is a blocking protocol. After voting yes, a participant holds its locks and cannot decide alone; if the coordinator crashes before announcing the outcome, participants are stuck "in doubt" holding locks until it recovers. It also adds round-trips, so latency is the sum of the slowest participants, and availability drops because every participant must be up. In interviews, mention it exists and why you avoid it across services; prefer keeping the data in one database or using a saga.

Step 6Saga

A saga replaces one big distributed transaction with a sequence of local transactions, one per service, each with a compensating action that semantically undoes it. Book flight, then book hotel, then charge the card; if charging fails, run "cancel hotel" and "cancel flight". There are no cross-service locks, so it stays available and fast, but there is no isolation: other requests can see the intermediate states, so you design for it (for example, with the hold pattern above). Sagas are coordinated either by an orchestrator or by events (choreography). The mechanics, failure handling, idempotency and orchestration engines such as Temporal and Step Functions get a full deep dive in 07 · Multi-Step Processes.

Step 7Serialize through a single queue (single writer per key)

If you cannot tolerate contention at all, remove concurrency instead of managing it: route every operation on a given entity through one ordered consumer, so operations on that entity run one at a time. No two writers ever race, so no locks or version checks are needed for that entity.

  • Partition by entity id. Use a message log such as Kafka and key messages by seat_id or auction_id. All messages with one key land in the same partition, which is consumed in order by exactly one consumer in a group. Different keys are processed in parallel across partitions, so throughput scales with the number of partitions.
  • The actor model (Akka, Orleans, Erlang/Elixir processes) is the same idea in memory: each entity is an actor with a mailbox, and it processes one message at a time.
  • Bidding example: every bid for an auction goes to that auction's partition; the single consumer checks "is this higher than the current best?" and applies it. Order is the arrival order in the partition.

Pros

  • Eliminates races for a key; simple per-key logic
  • Natural ordering and audit trail
  • Handles extreme hot keys without retry storms

Cons

  • Throughput for one key is capped at one consumer
  • Asynchronous: the user gets an answer later (status polling or push)
  • Consumer failover must be handled; hot partitions and rebalancing complicate it
  • More moving parts than a conditional UPDATE

Trade-offs & pitfalls

This is where interviews are won. Every contention technique trades one cost for another; be ready to say which.

Correctness versus throughput

The stronger the guarantee, the less parallelism you get. Locks and queues serialize access to a hot key; optimistic control keeps parallelism but wastes work when it guesses wrong. Pick by contention level: low contention favors optimistic, high contention on a few rows favors pessimistic, atomic updates or queues.

Hot rows

One row everyone wants (the last ticket, a viral item's stock counter) limits throughput regardless of technique, because updates to a single row are inherently serial. Options: use atomic decrements (shortest possible lock time), split a counter into N sub-counters or "buckets" and sum them, pre-allocate inventory slices per server, or shed load early with a queue or waiting room so only a controlled number of attempts reach the database.

Deadlocks

Acquire locks in a consistent global order, keep transactions short, set lock timeouts, and always be ready to retry a transaction the database aborted as a deadlock victim.

Retry storms and livelock

Optimistic loops multiply load exactly when the system is struggling. Use exponential backoff with jitter, a bounded attempt count, and consider a circuit breaker or switching the hot path to a different strategy.

Idempotency

Clients retry on timeouts, and you may retry on conflicts. Give each purchase attempt an idempotency key (stored with a unique constraint) so a repeated request returns the original result instead of buying twice.

Fairness and user experience

When 100,000 fans chase 5,000 seats, correctness is the easy part; the experience is not. Consider a virtual waiting room that admits users at a controlled rate, and tell losers fast and clearly instead of letting them spin.

Cross-system coordination is costly

Every step beyond one database adds failure modes (lease expiry, in-doubt participants, missing isolation). Prefer a design where the contended invariant lives in one place, and use sagas, outbox patterns and idempotent consumers for the rest.

When NOT to use it

  • Don't add coordination where there is no contention. If each user only edits their own data, there is nothing to race on. A distributed lock around a per-user update is pure overhead.
  • Don't reach for distributed locks, 2PC or sagas when one database will do. The fix for most contention is a conditional update or FOR UPDATE in the database you already have. Splitting data first, then coordinating, creates the problem you were trying to avoid.
  • Don't use optimistic control on a hot row. If most attempts will collide, you get retry storms. Use an atomic update, a pessimistic lock or a queue there.
  • Don't hold locks across user think-time or external calls. Use OCC or a hold-with-expiry instead.
  • Don't use a lock service as a correctness guarantee unless it is paired with fencing at the resource.
  • The real problem is write volume, not conflicts. If writes are to many different rows and the database simply cannot keep up, that is Scaling Writes, not contention.

Interview script

Say it like this
"The risk here is a race condition: two buyers both read that one seat is left and both buy it. The invariant is that a seat is sold at most once. I'd keep ticket state in a single relational database and enforce that with an atomic conditional update: UPDATE tickets SET status='sold' WHERE id=? AND status='available', checking rows affected. Because users spend minutes in checkout, I'd model a hold: available, held with an expiry, then sold, so no lock is held across user think-time. Where logic spans several rows I'd use SELECT FOR UPDATE with consistent lock ordering, or optimistic concurrency with a version column and retry with backoff if conflicts are rare. I would deliberately not shard the contended data prematurely, since that pushes me toward distributed locks, two-phase commit or sagas. If a single item becomes extremely hot, I'd put a queue in front of it keyed by item id so one consumer serializes the writes, and I'd add idempotency keys so client retries never double-buy."

Deep-dive Q&A

Why isn't wrapping the read and write in a transaction enough?

Under the default read committed level, a transaction only guarantees that each statement sees committed data. Another transaction can commit a change to the same row between your SELECT and your UPDATE, so your decision was made on stale information. You need the check and write to be atomic (a conditional UPDATE), a lock on the row (FOR UPDATE), a version check, or serializable isolation with a retry loop.

Optimistic versus pessimistic: how do you choose, and what happens if you pick wrong?

Estimate how often two requests hit the same row. If conflicts are rare, or users hold data a long time before submitting, use optimistic control: no locks, a retry or 409 on the rare collision. If conflicts are common or the work between read and write is costly to redo, use pessimistic locking so waiting replaces thrashing. Pick optimistic on a hot row and you get retry storms, wasted work and starvation; pick pessimistic for a form with long think-time and you get blocked users, tied-up connections and abandoned locks. You can mix: optimistic for the general path, an atomic update or lock for the known hot path.

Walk me through optimistic concurrency control. What exactly happens when two users edit the same row?

Both read the row and see version 7. Each computes their change with no locks. The first to write runs UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = 7; one row is affected and the version becomes 8. The second runs the identical statement, but the row is at version 8, so zero rows match: a detected conflict. That client must redo the whole read-compute-write (re-read to see version 8, re-validate, recompute) with backoff and jitter and an attempt cap, or return 409 to the user. Pitfalls: bump the version in the same statement; retry the whole operation, not just the write; keep side effects idempotent; remember a per-row version does not guard multi-row invariants (write skew); and prefer a monotonic version over comparing values to avoid ABA.

Why can't I just use a Redis lock to protect the seat?

You can for efficiency, but not as the only correctness guarantee. A Redis lock has a lease; if the holder pauses (GC, network, VM stall) past the lease, the lock expires, a second client acquires it, and then the first resumes and writes, so two clients act as the exclusive owner. Safety requires a fencing token checked by the data store, which is really an optimistic version check on the resource. If the seat is already in a database, a conditional update there is simpler and strictly safer, and the Redis layer is better used for short holds with TTL or as a fast pre-filter.

How do you handle a flash sale where 100,000 users want 1,000 items?

Expect a very hot row. Use atomic decrements (qty = qty - 1 WHERE qty > 0), which hold locks for the shortest possible time, or split inventory into buckets to spread the contention. Protect the database with a virtual waiting room or a queue that admits users at a controlled rate, reject quickly once stock hits zero (a cached "sold out" flag avoids touching the database), use holds with short expiry for checkout, and add idempotency keys. If a single key still saturates, serialize it through a partitioned queue keyed by item id.

Two-phase commit versus saga: when would you choose each?

2PC gives atomic all-or-nothing and isolation across a small number of tightly controlled databases, but it blocks if the coordinator fails and hurts availability and latency; it is rare across independently owned services. A saga gives availability and loose coupling by running local transactions and undoing them with compensations, but offers no isolation, so intermediate states are visible and compensations must be idempotent and designed carefully. For microservice workflows choose sagas; if the data can be kept in one database, avoid both and use a plain transaction. See Multi-Step Processes.
